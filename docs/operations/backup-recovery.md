# 备份与恢复

本手册适用于 Semlia 应用状态的受控恢复，不授权删除、接管或重置现有环境。收敛版 1.0 的实际合成恢复证据见 [T004](../evidence/V1-T004/consumption-restore.md)；最终候选门禁和用户验收见 [T005](../evidence/V1-T005/)，不据此承诺企业 RPO、RTO 或 SLA。

## 完整恢复集

| 内容 | 要求 |
| --- | --- |
| 应用 PostgreSQL 数据库 | 一致快照，含身份、授权、知识、不可变 revision/release、治理、来源密文、审计与迁移状态 |
| content | Git 投影及其完整元数据、历史和必要文件，不能只复制空目录 |
| inputs | `SEMLIA_SOURCE_ARTIFACT_ROOT` 下注册的输入内容；native 默认与 content 共用目录，应明确记录去重关系 |
| artifacts | 本地上传内容，或 S3/object store 的对应对象及版本；对象存储不包含在 PostgreSQL dump 中 |
| 加密与运行配置 | 原 `SEMLIA_SECRET_KEY`、配置版本、模型 credentialEnv 对应秘密、认证/OIDC/对象存储配置和恢复所需凭据 |
| 外部来源连接 | 发现来源密文及能解密它的原密钥；执行映射、执行专用只读凭据及 TLS/网络依赖 |
| 运行身份 | 应用版本、平台、schema、二进制及文件清单摘要、owner/marker、端口和依赖归属 |

外部业务数据库及其他来源内容需要其各自的备份策略；应用备份不复制它们，也不恢复 PostgreSQL 集群的外部角色。查询结果行是临时数据，不能承诺恢复已显示的结果表。记录会话策略：完整 DB 快照含会话记录，但不应复制或传播浏览器 cookie；恢复验收使用新建的正常密码会话，并按安全策略处置既有会话。

## 一致备份

1. 核对应用、数据库、角色、文件目录和容器的明确归属，记录版本、schema 和非秘密清单；未知或同名资源不是可接管目标。
2. 在授权窗口停止该应用的 server、worker 及其他写入者，或采用经验证的一致性方案。只停止自有服务；共享 PostgreSQL 不停机。等待进行中的治理写入、作业和迁移结束。
3. 对应用数据库创建受保护的逻辑/物理快照；复制 content、inputs、artifacts 和所需配置、密钥。逻辑恢复若使用 `--no-owner --no-acl`，需为新目标明确重建最小权限，不能把旧管理员作为运行账号。
4. 建立完整文件清单、字节数和摘要，明确每个非空库的实际内容。拒绝路径穿越、符号链接、未知文件集合和拷贝中变化；密钥文件也在私有回执中核对摘要。目录 `0700`、私有文件 `0600`，备份另加合适的离线/加密保护。
5. 核对快照可读取后恢复原自有服务并验证 readiness。不要在备份成功前删除旧状态，也不要公开 dump、环境文件、密文、会话或日志原文。

## 恢复到新目标

1. 在已登记 PostgreSQL 实例建立新的专用数据库及非特权角色，记录 owner/marker。每次写入前重新确认目标归属、空 schema/表和空目标目录；发现未知内容立即停止，不清空它来通过检查。
2. 核对备份身份、schema、完整清单、实际文件摘要和密钥，先确认恢复材料齐全。恢复数据库及各文件库到新目标，保持明确路径和最小权限；应用不得使用基础设施管理员凭据。
3. 恢复原加密根密钥及必要外部配置，使用目标数据库的新专用连接配置。不要用新随机密钥替代旧密文的密钥。若要轮换，须另行完成重加密、外部凭据轮换和恢复验证。
4. 在启动验证请求前，对比数据库关键表或完整表集合的行数及稳定内容指纹，对比三个文件库实际字节摘要；仅看到目录存在、schema 相同或健康页可访问不足以证明恢复。
5. 启动目标 server/worker，正常认证读取工作区、权限、知识和 exact release/revision/manifest；通过普通 artifact preview API 核对支持类型的内容摘要。SQL 注册/发现 adapter 不提供内容预览，HTTP 422 不代表其已备份字节丢失；使用 Markdown 等受支持内容验证预览路径。
6. 对合成来源执行正常 `/sources/{id}/test` 等确实读取数据库密文并解密的操作，证明恢复密钥有效。不能仅注入明文执行 DSN、读取元数据或调用健康页作为密钥恢复证据。不要为恢复验证发送真实客户内容到模型。
7. 核对外部来源未被修改、原环境与原配置仍保全；确认服务、任务、端口、角色和数据归属后才安排正式切换。失败时保留原环境、新目标和失败证据，禁止自动覆盖原库重试。

## 升级与限制

当前应用要求 schema 33、非 dirty。已验证升级基线为隔离的 schema 32，含正常账号、工作区、principal 与 membership；不代表任意旧七类原型或任意生产数据升级兼容。对真实已有数据先复制到新目标演练、记录结果，再申请切换；不强制修改 migration version，不对含 Ask 数据的库自动降级。

完整恢复演练证明合成样本的具体边界，不替代容量、灾难场景、对象存储版本保留和异地备份测试。开发工具输出发生过私有配置披露，生产前需轮换受影响凭据；轮换计划不得遗漏原密钥解密能力及外部来源账号。所有回执只公开非秘密元数据和验证结果。
