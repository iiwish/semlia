# 数据语义中台汇报设计

## 汇报结构

对象为已召开启动会的项目领导。汇报分为知识加工、知识使用两部分，不重复立项背景。全稿 13 页，包含原型演示与方案讨论，不设置附录。建议讲述与演示合计 14–17 分钟，另留时间听取指导意见。

同一个问题贯穿全文：“上个月，华东地区老客户的客单价是多少？”先介绍加工方法与五类知识全貌，再展示实际保存的信息，最后用同一批信息完成需求解析、数据定位、SQL 与结果演算。

| 页码 | 内容 |
| --- | --- |
| P01 | 数据语义中台，知识加工与业务问数 |
| P02 | 两段流程总图，已发布知识连接加工和使用 |
| P03 | 五类知识总览，逐类对照保存内容与使用作用 |
| P04 | 对象属性、老客户判定与客单价公式 |
| P05 | 客户相关来源的区分与数据资产字段说明 |
| P06 | 独立成员绑定、多对一关联与场景驱动的模型沉淀 |
| P07 | 完整问句展开为订单侧和客户侧需求 |
| P08 | 复用模型、无模型按需规划、依据不足待验证三种情况 |
| P09 | 指标、资产映射与关联、口径对应 SQL 三个部分 |
| P10 | 七笔合成订单筛选与 200 元/单的结果演算 |
| P11 | 对话分别沉淀用户偏好与系统通用知识 |

| P13 | 说明框架原型阶段，请领导指导设计方向、优先场景和推进重点 |

P02 交代加工与使用的整体流程，审核职责和输入材料说明保留在讲稿，不单列加工步骤页。P03 直接展示五类知识全貌，P04–06 展开内容。P06 上方展示业务属性到两份资产的独立映射和多对一关联，下方用三步说明模型按真实场景形成并复用，不枚举全部分析组合。P07 展开同一个问题的业务需求，P08 用三个互斥情形展示规划路径；模型复用和无模型规划使用同一批获准依据，缺失依据进入验证，不直接取数。

P09 指认 SQL 的计算、数据、条件分别来自哪些知识，不逐行朗读。P10 讲清纳入、排除及分母选择。P12 演示控制在约 3 分钟，回到 P13 听取领导意见。收尾先说明原型以框架和主要流程展示为主，业务规则、交互细节与真实场景验证仍需完善。以三个开放问题邀请领导指导，不把设计方案、试点范围或排期呈现为定案。小范围试点思路保留在讲稿中，供进一步讨论。

## 投影视觉

采用白底、深色正文与少量蓝绿强调。全稿使用固定 1440x810 的 16:9 画布，按整体比例适配桌面投影，安全边距 72px，字距为 0。

- 标题 52px，封面 90px。主要图文 26–35px，字段和 SQL 24–25px，必要来源注记 18px。
- 背景为白色，正文 #18221d，辅助文字 #56635c。蓝色 #2851ca 表示定义与需求，绿色 #096b50 表示数据实现与确认结果，赭红 #a0442c 区分条件或计算层次。
- 每页围绕一张主图、一个结构或一个结果。重复解释和校验细节放入讲稿，屏幕保留影响理解与结论的内容。
- 流程使用大步骤序号，业务规则使用直接判定表达与分式，数据资产使用来源对照和字段表，模型使用可编辑关系图。
- P03 的总览表保持五行，类别、保存信息与用途分别形成清楚的文字层次。P07 的四个问句片段以相同结构展开需求。
- P06 保留左右资产字段表，中间标明统一客户键和多对一关系；下方是场景驱动、引用关系、审核复用的连续步骤。P08 用三行条件、动作与结果对照，不把互斥分支画成连续步骤；绿色强调共同执行门槛，赭红标识待验证分支。
- P09 的说明分组按 SELECT、JOIN、WHERE 的行组对齐，保留完整说明性 SQL。P10 放大结果，使用浅绿标识纳入订单。
- P11 从用户对话分为两列：蓝色用户偏好、绿色通用知识。每列只展示适用范围、一个对话例子和生效路径；个人确认与通用审核发布明确区分，不画成一条连续审批链。
- P13 上方说明框架原型的成熟度，中间三列分别提出设计方向、优先场景和推进重点的问题，下方简短说明将根据意见完善方案。保持白底与充分留白，便于停留讨论。
- 不使用暗色幻灯片、装饰性图片、渐变背景或嵌套卡片。历史原型截图保持原图，支持放大查看，注明时间与证据边界。

交互包括分页、目录、逐页讲稿、全屏、连续阅读、打印和截图放大。支持键盘、可见焦点与减少动态效果。目录、页码与打印均为 13 页。

## 内容边界

五类知识为业务对象、业务口径、指标、数据资产、分析模型。属性归对象，判定归口径，基础聚合与派生计算统一归指标。对象和指标自身包含定义，不额外创建同名概念。

数据资产引用来源版本，保留表字段、类型、业务含义、身份、粒度、时间、质量与使用限制。知识整理不替代事实数据清洗，去重、身份合并与派生字段必须有真实加工依据。

P02 讲稿说明数据血缘是后续接入的补充材料，当前尚未具备该接入能力。血缘用于辅助识别来源、核对加工与依赖，并支持变更影响分析，不替代业务口径确认，也不是启动知识加工的前置条件。正文保留来源、整理确认、发布三段主流程，不堆叠职责和验证细节。

成员绑定与关联契约是独立可寻址、可验证发布的实现记录，不增加面向用户的第六种知识类型。分析模型引用常用记录，固定场景、粒度、默认值和使用约束，不保存明细或独占映射。客户条件通过业务成员找到客户资产实现，不由客单价名称单独推出。

有适用模型时优先复用；无模型但已发布依据完整且策略允许时，由 LLM 在有界范围内组合临时计划；未知关系或含义歧义只形成候选。两条可用路径均校验整个计划的身份、时间、粒度、连接扇出、必要过滤、版本、权限和预算，不能借无模型路径绕过场景政策。字段齐全和执行成功不等于业务正确。

模型由真实试点、常用报表或 SQL 的复用需求驱动，AI 提出草稿，负责人确认、验证和独立审核后发布。能力索引按指定版本依赖校验生成，不复制指标定义，不作为执行授权。月份、地区和筛选组合只改变查询参数；临时计划与高频问题不自动产生或发布模型。

发布固定经过业务确认、系统验证和独立审核的兼容版本组合。实际源数据不因此冻结，查询和对账仍需记录数据时间或快照。多个实现有业务含义差异时澄清，无适用实现时报告缺口。

五类知识结构入口不等于独立关系治理、能力索引与无模型规划已经完成。P12 的历史验收截图只说明对应工程基础，不能证明当前工作区已经完成两条取数路径和真实业务闭环。P13 将当前原型定位为框架展示，后续方案、验证范围和实施安排结合指导意见与真实业务条件细化。

## 案例与文档

P09 是手工编写的生成结果示意，不是原型输出。花括号为待核实的绑定，冒号为本次参数。公式、条件、映射与关联预先确认发布；具体 SQL 按模型复用或按需组合得到的查询计划生成，执行仍需验证、授权与预算控制。

P10 使用 `case-example.json` 的七笔订单和四位客户，固定演算 2026 年 8 月。采用客户当前区域、全历史首次有效支付日期及样例有效订单标记，纳入 O01、O02、O03。金额为 600 元，订单数为 3，客户数为 2，客单价为 200 元/单。首次支付日期不从本月样本临时求最小值，`is_valid` 不替代企业真实有效订单口径。

对话反馈有两条长期沉淀路径。用户偏好经明确记忆要求或用户确认后，在当前工作区对该用户生效，可修改、删除和停用，不覆盖业务口径或权限。系统通用知识先形成口径、资产或关联等修订候选，检查共享授权、证据和敏感信息，验证与独立审核发布后限获准业务范围复用，不默认跨用户公开对话或跨租户共享。

这两条路径按适用范围划分，不改变五类业务知识结构。一次对话可分别包含偏好和业务纠正，逐项分流；仅本次有效的选择不默认长期保存。P11 以“经营分析中的销售额不包含集团内部交易”说明用户补充数据库结构无法单独确定的业务规则。该陈述是待确认的示例，需核对业务依据、适用范围与数据实现，不代表企业现行口径，也不改变前文客单价案例。个人偏好管理与通用知识分流均为目标能力，不表示已启用长期记忆或自动知识发布。

## 检查

`build/semantic-briefing/prepare-deck.mjs` 统一 13 页的 ID、标题引用和页码。`qa-v2.mjs` 检查 1440x900、1024x768 和 1920x1080 下全部页面、键盘、讲稿、离线运行、截图放大与打印，确认目录无附录、P02 讲稿保留审核与血缘边界、P03 为知识总览、P06 独立映射与 P08 三条处理分支完整。JSON 结构检查确认模型和临时计划引用同一组独立记录，示例不可执行且不自动发布知识。

`check-case-example.py` 在内存 SQLite 中将说明性 SQL 绑定为合成表，核对 600 ÷ 3 = 200，以及空结果、排除条件和日期边界。不接触真实数据库，不代表应用端到端验收。

`check-planning-example.mjs` 检查五类结构、独立记录引用、可选模型与示例不可执行边界，并核对原有 SQL 和原型截图保持一致。这是文档一致性检查，不是无模型规划功能测试。

检查材料位于 `build/semantic-briefing/projection/`，不作为汇报正文。
