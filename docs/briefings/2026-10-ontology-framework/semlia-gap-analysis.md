判断标准：

- **具备**：代码已实现，并有验收证据。
- **部分**：有实现但覆盖不全，或只有设计。
- **缺失**：设计和实现都没有。

## 0. 结论

**一句话**：Semlia 在"编译器"和"凭什么信"两层做得比框架要求的还严。短板集中在框架所说的"制度层"：

- 同一概念的多个正当口径怎么并存；
- 业务方怎么质疑、怎么裁决；
- 一个数字能不能事后被引用；
- 问数失败能不能反过来驱动治理。

**做得好的地方**

1. **LLM 只负责理解，正确性交给确定性链路。** 模型只输出受 JSON Schema 约束的结构化查询，解析、拒绝、编译和只读执行都在服务端完成。同一说法指向多个资产时，服务端直接澄清，不调用模型。
2. **"说什么"和"怎么算"真正分开了。** 别名、易混淆项、典型问题、取值别名都作为受审词汇随修订发布。"计算核心"摘要让只改词汇的修订不会让引用失效，这就是语义三角里符号与概念的分离。
3. **构成性规则可以执行。** 业务口径的判定表达式把"老客户 = 首次有效支付日期 < 统计期开始日"变成带参数、可校验的规则。
4. **证据有认识论分级。** 证据分声明、约束、推导、观察、推断五类，业务规则必须有声明类证据才能确认。关系也区分已断言、推断、候选和废弃。
5. **防重复计数，也防"平均的平均"。** 编译器只接受一对一和多对一连接，多对多直接拒绝。派生指标必须从输入重算，零分母返回空值。执行时还会再校验业务键唯一。

**主要差距**

1. **只做到了"歧义不行"，还没做到"多义可以"。** 适用情境（scope）是自由文本。财务、管理、考核口径只能建成几个互不相干的资产，靠文字说明区分，每次提问都要澄清。没有口径族，没有按情境选默认口径，也没有差异披露。
2. **治理流程以作者为中心。** 消费者在答案上"指出问题"需要提案权限。问数的拒绝、澄清和失败不会进入待办，使用事件也只记录目录读取和搜索。所以飞轮的前半圈还没接上。
3. **答案的出生证明太技术化。** 答案卡显示的是 release、修订 ID、计划摘要和 Agent run，看不到负责人、批准人、口径版本名称和数据截至时间。结果行不落库；执行记录只保存计划摘要、结果摘要和行数，能证明是哪一次执行，但事后看不到数值本身，也没有面向业务的引用入口。
4. **范畴和时间只覆盖了一半。** 业务对象不区分实体、事件、角色。指标没有存量与流量的时间聚合语义。定义没有业务生效期，口径变更后历史数要不要重述也没有规则。
5. **互操作缺开放标准。** 解析与引擎无关，也有 Git 投影，但还不支持 OSI、dbt MetricFlow 这类格式的导入导出。

**最值得先做的三件事**（详见第 9 节）

1. 让质疑和语义缺口进入待办，飞轮才能转起来。
2. 把答案的出生证明改成业务人员看得懂的样子，并落一张不含明细的观测回执。
3. 建立口径族和结构化情境，再在上面做口径差异桥。

### 2.1 能拦住哪些范畴错误

| 框架列出的范畴错误 | Semlia 能否拦住 |
| --- | --- |
| 把角色当类型 | 不能。没有"角色"这个概念，"客户"既可以建成对象，也可以被当作分群 |
| 把存量当流量 | 不能。聚合函数里有 sum，但没有"跨时间只取期末值"这类声明 |
| 把比率、单价当成可加的量 | 能。派生指标强制从输入重算，比率不会被直接相加或平均 |
| 一个词背后有三种对象（订单是事件、承诺还是单据） | 部分。数据资产区分事件时间和快照时间，业务对象本身不区分 |
| 没声明关系基数，导致重复计数 | 能。连接契约必须声明基数，编译器拒绝多对多，执行时校验键唯一 |

## 3. 元模型四问

| 问题 | 评价 | 说明 |
| --- | --- | --- |
| 说什么 | 强，超出框架要求 | 词汇作为受审字段管理，发布前检查别名冲突，并重放典型问题 |
| 是什么 | 中 | 有五类知识、三个关系平面（分类、语义、依赖）和断言状态；缺情境对象，也不区分对象范畴 |
| 怎么算 | 强 | 封闭表达式、聚合与派生、带参数的判定、连接契约、计划校验；缺存量/流量 |
| 凭什么信 | 强 | 证据分五类（[迁移 000003](../../../migrations/000003_semantic_registry_foundation.up.sql#L314)），业务规则必须附声明类证据（[迁移 000028](../../../migrations/000028_production_business_rules.up.sql#L43)）；验证、审核、发布绑定同一份内容。演示数据没有附证据，就绪度如实停在 5/6，这不是能力缺失 |

### 3.1 两条架构原则

**概念、口径、数值分开。** Semlia 有意不给对象和指标再建一个"同名概念"（见[知识类型 §1](../../specs/knowledge-to-data/knowledge-types.md#1-设计原则)）。我认为这个取舍对了一半：

- **对的一半**：对象和指标自带定义，不需要再套一层"概念"，这符合最小本体承诺。
- **缺的一半**：一个概念有多个正当口径时，需要一个轻量的"口径族"关系把它们连起来，否则差异桥和按情境选默认口径都无处落脚。建议加一种关系，不加新的一级类型。
- **数值层**：结果行不落库是出于隐私，合理。执行记录（`query_execution_runs`）已经保存了计划摘要、结果摘要和行数，离"观测回执"只差两步：补上数据水位，提供面向业务的引用入口。少量汇总值要不要保存，交给工作区策略决定。

**事实不可变，解释可以改版本。** 这一条是一致的：客户事实留在数据源，知识 release 不可变，回滚会生成新的 release。缺的是"按新口径重算历史"的显式规则，见第 2 节"时间"一行。

## 4. AI 带来的成本结构变化

| 框架推论 | Semlia 现状 | 判断 |
| --- | --- | --- |
| 重心从建模工具转向裁决与验证 | 生产流程是候选 → 草稿 → 验证 → 独立审核 → 发布；批量确认已实现；风险规则可解释 | 具备 |
| 领域负责人能在十分钟内批完一个定义 | 审核入口是工程式的提案评审；流程里有业务专家确认口径这一步，但没有专门入口；待办按优先级、风险、截止时间排序，没有按"影响面 × 置信度"排 | 部分 |
| LLM 负责理解，编译器负责正确 | 模型输出要过 JSON Schema 门禁；知识摘要一变，本次回答就作废；服务端消歧时不调用模型 | 具备，且比框架更严 |
| Agent 是一等用户 | MCP 提供搜索、描述、解析、计划、执行、取消，只读已发布语义 | 具备 |
| 信任分级 | 发布侧有 G0–G3，自动发布后置；消费侧不区分"领域内批准"和"企业认证"，代码里也没有认证等级 | 部分 |

## 5. 用户与界面

- **答案卡适合审计，不适合业务人员。** 标题显示 release、定义数量和 Agent run；语义计划显示计划摘要、模型修订和"受治理对象"数量（[KnowledgeViews.tsx:121](../../../web/src/KnowledgeViews.tsx#L121)）。业务人员真正想知道的是：负责人是谁、谁批准的、口径叫什么、第几版、数据截至什么时候。这些都看不到。
- **消费者没法质疑。** "指出问题"之后的"修订相关知识"需要 `asset.propose` 权限（[KnowledgeViews.tsx:146](../../../web/src/KnowledgeViews.tsx#L146)）。没有这个权限的人只能改自己的问法，没法把"我觉得这个数不对"交给负责人。
- **界面术语偏工程。** "本体关系""上位于 / 下位于 / 互斥于""分析模型""成员绑定"对所有角色可见。首批目标用户是数据团队，这可以接受；但业务确认者需要一个只讲定义、差异、证据和批准的入口。

## 6. 切入点、关键功能与飞轮

| 框架功能 | 现状 | 判断 |
| --- | --- | --- |
| 口径差异桥 | 能对比两次发布之间的差异；不能对比两个口径的结构，也没有量化瀑布 | 缺失 |
| 带出生证明的答案 | 技术依据齐全（release、修订、SQL、参数、策略版本），可以跳到修订证据；缺业务化的呈现、负责人与批准人、数据水位、其他口径下的值；数值不落库，执行记录只有计划摘要和结果摘要 | 部分 |
| 一键质疑 | 有"指出问题 → 修订相关知识"，但只开放给有提案权限的人，而且直接开修订，不形成可统计、可路由的争议 | 部分 |
| 变更影响面 | 发布详情能看到受影响的消费者（跟随最新版本的和固定版本的）；引用固定到修订，计算核心一变就要求重新固定；缺"谁会看到不同的数"和历史重述；血缘未接入 | 部分 |
| 拦截近似重复的口径 | 同类资产的名称或别名冲突时，必须声明为易混淆项，否则不能发布；不检测"算法近似"（输入相同、聚合相同、过滤条件高度重叠） | 部分 |
| 飞轮 | 待办只有审核、验证、来源、运行、兼容五类（[workbench/model.go:21](../../../internal/domain/workbench/model.go#L21)）；使用事件只记录目录读取和搜索；问数的拒绝、澄清和失败只留在问数记录里 | 缺失 |

飞轮需要的数据其实已经有一半了：`semantic_queries` 保存结构化请求和"已解析 / 被拒绝"的结果，`semantic_refusals` 保存拒绝码和有权查看的候选资产，`ask_requests` 保存"成功 / 澄清 / 失败"状态。即使不存原始问题，也能按"资产 + 拒绝码"算出需求覆盖和缺口。缺的是服务端澄清时的候选资产和触发澄清的已发布说法，这两项目前没有记录。

## 7. 度量

- SSOT 当前的北极星指标是"完整生产闭环通过率"，属于交付期指标，适合现阶段。长期指标"每周可信语义消费数"按消费量计。
- 建议在消费量之外补三个指标：
  - **被质疑率**：可信回答率的反面；
  - **需求加权覆盖率**：按被问到的资产计，不按编目数量计；
  - **争议解决时长**：SSOT 已有"提案到发布的中位时间低于 1 个工作日"，可以先用它近似。
- 目前所有验收用的都是项目自己生成的合成数据（见 [V1 规格](../../specs/v1-convergence/spec.md#数据与执行授权)），还没有真实领域的试点数据来衡量这些指标。这是现阶段最大的未知数。

## 8. "不做什么"的对照

| 框架里的"不做" | Semlia 现状 | 判断 |
| --- | --- | --- |
| 不做本体编辑器 | 没有本体编辑器，分类关系也不能编辑；但"本体关系"作为页签名和术语露在界面上 | 基本一致 |
| 不做自上而下的大一统模型 | 模型按真实场景沉淀，不按指标、月份、地区的组合去枚举 | 一致 |
| 不教条地套用 RDF/OWL | SSOT 明确不以 RDF/OWL 为前提，也不把"未知"自动判为"否" | 一致 |
| 不做没有语义支撑的 NL2SQL | 只用已发布语义，有歧义或缺依据一律拒绝 | 一致，且更严 |
| 不把语义锁进 BI 或引擎 | 与引擎无关，Cube 可选，有 Git 投影 | 一致，但缺开放标准 |
| 少讲"中台" | 对外叫"开放语义资产控制平面" | 一致 |

## 9. 建议

### 9.1 按优先级

| 优先级 | 建议 | 补的差距 | 可复用的现有能力 | 工作量 |
| --- | --- | --- | --- | --- |
| P0 | **质疑和缺口进入待办。** 新增"质疑"和"语义缺口"两类待办。有问数权限的人就能发起质疑，按资产路由给负责人。问数的拒绝和澄清按"资产 + 拒绝码"聚合成缺口 | 飞轮、一键质疑 | 待办模型、`semantic_queries`、`ask_requests`、搜索已在用的 HMAC 指纹 | 中 |
| P0 | **答案的出生证明业务化。** 答案卡显示口径名称和版本、负责人、批准人和批准日期、数据水位（不知道就写"未知"），并提示易混淆的口径；技术 ID 收进折叠区 | 出生证明 | 发布审核记录、`ownerPrincipalId`、`confusableWith` | 小 |
| P0 | **加上三个指标的埋点**：可信回答率、被质疑率、需求加权覆盖率 | 度量 | 同上 | 小到中 |
| P1 | **观测回执。** 在现有执行记录（已有计划摘要、结果摘要、行数）上补数据水位和面向业务的引用入口；少量汇总值要不要保存由工作区策略决定 | 数值层 | `query_execution_runs` | 小到中 |
| P1 | **口径族和结构化情境。** 新增"同一概念的不同口径"关系；把 scope 拆成用途、业务域、适用角色和生效期；"场景默认口径"作为受治理的配置发布，而不是个人偏好 | 多义可以 | 关系平面、分析模型的 `compatibleTermRefs` | 中到大 |
| P1 | **口径差异桥。** 先做同族口径的结构对比（输入、过滤、时间、单位）；配置了执行能力后，再做逐项量化的瀑布图 | 差异桥 | 编译器、同一快照对账 | 先中，后大 |
| P1 | **补全范畴。** 指标增加时间聚合语义（流量求和，存量取期末），规划器拒绝跨期加总存量；业务对象增加种类（实体、事件、快照） | 范畴 | 生产校验、规划器拒绝码 | 中 |
| P1 | **检测算法近似的指标。** 输入相同、聚合相同、过滤条件高度重叠的新指标，必须合并或写明区别；照搬词汇冲突门禁的做法 | 近似重复 | 生产校验门禁 | 小到中 |
| P2 | **定义生效期与历史重述。** 修订带业务生效期，支持按业务时点解析；变更时声明"重述"还是"保留"；层级成员可以按旧架构或新架构解析 | 时间 | release 与修订 | 大 |
| P2 | **语义级敏感分级。** 敏感级别改成枚举，挂到属性和成员上，传到绑定、回答和 MCP 响应；和条件授权阶段一起做 | 应然 | RBAC 作用域 | 大 |
| P2 | **开放格式导入导出。** 已发布的指标和模型可以导出为 OSI 或 dbt MetricFlow 格式；dbt 语义模型可以作为候选导入 | 互操作 | Git 投影、dbt 工件导入 | 中 |
| 后置 | **动作语义。** 继续后置，元模型里先留好位置 | 行动 | — | — |

### 9.2 产品层面

- **下一个里程碑应该是真实领域试点，而不是更多治理机制。** 选三五十个核心指标，用可信回答率、被质疑率和争议解决时长来验收。现在的治理机制（G0–G3、三通道审核、批量确认、兼容性）已经跑在价值验证前面了。
- **给业务确认者单独一个入口。** 只看定义、口径差异、证据和批准动作，和作者工作台分开。
- **定位保留"开放语义控制平面"，同时补上制度层的故事。** 平台自带的语义层（Snowflake、Databricks、微软）很难做口径并存、争议裁决和业务化的出生证明，这正是 Semlia 能拉开差距的地方。

## 10. 应该保留的 Semlia 取舍

- **不给对象和指标再建同名概念。** 用口径族关系补足，不新增一级类型。
- **原始问题和结果行不落库。** 用资产绑定、拒绝码、指纹和观测回执来替代。
- **自动发布（G2/G3）继续后置。** 在有真实试点的回滚率和抽检数据之前不放开。
- **只读执行，动作语义后置。**

## 附：核对范围与限制

- 结论来自阅读文档和代码，没有启动运行环境，也没有调用模型。
- "具备"以 `main` 上的代码和已有验收证据为准；SSOT 里只有设计的内容标为"部分"。
- 工作区里未提交的来源与接入界面改动（`LiveSourcesView`、`SourceContents` 等）没有纳入评估。
