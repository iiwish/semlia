## 1. 决策摘要

采用增量重构，不重写整个系统。保留模块化单体、PostgreSQL、既有身份授权、任务队列、模型适配器、Proposal/Validation/Review/Release 和唯一生产前端。围绕来源版本、冷启动生产、关联对象治理与服务端恢复补齐缺口。

规划七个串行任务。第一项核实可运行基线并完成关键数据与接口契约，随后处理五个产品切片，最后独立完成回归和验收。SP-T001 的详细契约必须通过审核才允许后续实现；本计划不把未确定的字段细节交给实现者随意发挥。

| 任务 | 产出 | 退出结果 |
| --- | --- | --- |
| SP-T001 | 真实基线、覆盖矩阵、生产数据模型与接口契约 | 确认复用边界、迁移和恢复设计，修正估算 |
| SP-T002 | 可复核的来源版本集合 | 未变化成员、改名、删除和部分扫描有明确历史语义 |
| SP-T003 | 候选到新资产/既有变更的服务端生产命令 | 无预置语义资产也能产生完整、可恢复的治理草稿 |
| SP-T004 | 关联对象验证、审核、发布与回滚 | 无消费者完成依赖闭合的语义发布，失败不能部分发布 |
| SP-T005 | 基于来源与证据的内部 AI 生产 | AI 建议进入同一生产命令，失败、纠正和归因真实 |
| SP-T006 | 连续的桌面生产体验 | 来源到 release 可操作、可核对、可恢复，不依赖本地缓存串事务 |
| SP-T007 | 端到端、迁移、兼容性与实际模型验收 | 三组样例和 SP-AC-001 至 SP-AC-012 的证据完整 |

首次生产、变更生产、失败恢复三组样例贯穿各任务，不留到最后才写测试。外部消费扩展、新连接器、移动端、通用 AI 平台和 G2/G3 不进入任务图。

## 3. 技术决策

### SP-TD-001 保留架构，只增加生产协调

生产协调放在现有应用层，连接 discovery、catalog 与 governance；不引入第二套语义仓库、审批系统或通用任务运行时。状态权威仍属于来源运行、Proposal、Validation、Review 和 Release。

需要持久化的生产操作仅记录幂等请求、输入快照、目标集合、关联提案和结果定位，不托管会话或业务调研。操作进度从权威对象推导，避免维护相互矛盾的第二份审核状态。

替代方案是拆微服务或由前端继续编排写入。前者增加事务与运维成本，后者不能支持清除缓存后的可靠恢复。任务影响：SP-T001、SP-T003 至 SP-T006。

### SP-TD-002 固定生产输入版本集合

为来源投影保存不可变成员和名称快照，引用实际 dataset/field revision、代码与证据；未变化成员仍属于本次有效集合，不强制制造新物理 revision。范围、适配器版本、覆盖状态和内容摘要进入版本标识依据。并发提交按来源和投影版本约束唯一性，失败或部分扫描不得静默取代完整有效集合。

生产输入固定所选来源集合、候选、规则证据及各自版本，并记录完整性和摘要。层间传递这些引用，不在历史读取时拼接最新名称。缺少可信历史的已有数据标记不可验证，重新扫描只能建立新的可靠版本，不能从当前值伪造过去。

替代方案是所有历史请求读 current 指针或每次扫描复制全部业务明细，均不采用。迁移采用增量表/字段及受约束索引，保留旧记录和旧读取契约；新生产入口对缺失必要历史证据失败关闭。任务影响：SP-T001、SP-T002、SP-T004、SP-T005。

### SP-TD-003 新建意图与更新意图分开

生产请求声明 `create` 或 `update`，包含候选与输入版本、目标内容、证据和依赖。`update` 固定已有目标及基础版本；`create` 使用明确的新建声明和待分配稳定身份，没有虚构的已发布基线。

一次数据库事务预留必要草稿身份、保存新建声明/结构化内容、创建关联提案与候选决策、记录幂等结果和审计。新建身份不代表内容已发布；验证器只在受约束的新建声明中解析本次目标，其他引用仍须存在且获授权。发布时才形成权威发布版本。具体 proposal intent 与旧表非空约束的兼容方案由 SP-T001 数据模型固定，SP-T003 实施迁移，不绕过约束手工造基础 revision。

一个生产请求可包含最多 32 个目标，每个目标最多 100 个变更项，总变更项最多 256 个；请求体同时受既有更严格上限约束。这覆盖首个样例，不设计无界批量导入。无实质更新不创建新提案；首次新建是明确的领域变化，不通过伪造 diff 触发发布。

替代方案是要求用户先创建空资产，或直接将候选标记 active，两者均不能满足受治理冷启动。任务影响：SP-T001、SP-T003、SP-T004。

### SP-TD-004 幂等与恢复归服务端

请求幂等键限定 workspace、当前主体及操作用途，绑定规范化内容摘要；同键不同内容冲突，同键重放读取原权威结果。每次重放和恢复都重新鉴权。候选、提案和目标的关联由关系约束与版本校验保证，不解析摘要文本判断一致性。

提供按操作标识读取和有界列表恢复入口；客户端失去响应或清空缓存后也能定位已有结果。提交、验证排队与发布分别使用各自幂等命令。不能把模型网络调用放进数据库事务；模型结果提交时重新核对授权与输入版本。

重试不扩大权限，不默认重放付费模型；未知结果先查询，不自动重新创建。任务影响：SP-T001、SP-T003、SP-T005、SP-T006。

### SP-TD-005 关联对象共同验证并原子发布

生产目标集合关联原有单目标 Proposal，冻结集合版本、提案内容摘要、来源输入及依赖图。复用原验证器与审核记录，增加集合级引用和粒度/Join 一致性检查；不是另一套审批状态机。集合内新对象可互相引用，但必须作为同一待审集合参与验证，不能把任意草稿当作已发布依赖。

发布命令在一个事务中重新核对当前授权、职责分离、输入版本、全体提案的有效验证与审核，写入全部新 pins、完整 manifest、提案终态、审计和 outbox。任意成员失败则整个发布不提交。旧单目标发布仍按原契约工作；属于冻结生产集合的成员不能通过旧单项命令绕过集合检查。

新增发布来源关联表达全部参与提案，保留旧单提案归因。旧 release 内容、digest 和响应语义不重写；读取方必须识别新的多提案归因，不能把它错误投影为某一个作者独占的发布。SP-T001 明确兼容响应，SP-T004 补齐发布详情、目录权威信息及投影读取。

回滚根据精确目标集合与先前 manifest 生成新 release；目标先前未发布时，恢复的是发布 pins 中的缺席，不删除身份或历史。依赖不闭合、过期审核、基线冲突与无权回滚均拒绝。

逐项发布作为替代方案不能保证相互依赖内容的一致交付，本阶段不采用。这里增加的是受限生产集合，不开放任意工作流或自动批准。任务影响：SP-T001、SP-T003、SP-T004、SP-T007，是估算中风险最高的部分。

### SP-TD-006 内部 AI 使用同一生产契约

扩展既有生成服务读取固定生产输入，输出 schema 约束的定义、目标局部引用、规则、证据和关系建议；服务端解析局部引用并分配稳定 ID。模型不得自行选择 workspace、授权主体或发布状态。

AI 输出经结构校验及当前授权检查后，通过与人工相同的生产协调命令创建提案。模型、配置版本、输入与输出摘要、调用状态、耗时和可用成本数据沿用 AgentRun/Step；不能虚构供应商未返回的费用。无模型、超时、无效输出、预算不足与来源指令注入都不生成成功结果或自动发布。

协议 stub 用于确定性回归，实际模型样例独立执行和评分。首次人工纠正必须改变实际定义或关系并重新验证，不只修改文案。无需第一方外部 AI 客户端或新增模型 SDK。任务影响：SP-T005、SP-T007。

### SP-TD-007 管理端围绕连续生产路径收敛

复用现有来源、知识、资产、治理和发布导航。主要改动是候选的新建/匹配操作、组合内容审查、固定版本证据、关联提案和恢复入口；剥离浏览器多步写入协调，把 localStorage 降为非权威草稿便利功能。

不做全站视觉重写或新增任务中心。对象详情不要求用户填写内部 ID，复用生成的 SDK/API 类型，保持 1440x900、1024x768、键盘、焦点与 reduced motion。任务影响：SP-T006。

### SP-TD-008 兼容性和证据先于清理

只追加受审迁移，不编辑已存在迁移；不删除已有消费者、凭据、release 或历史来源。公开生产管理接口与外部机器 allowlist 分离，不增加机器发布权限。发布集合复用既有 Release，MCP/CLI/SDK 的已发布消费契约继续回归。

新代码迁移采用 expand-first；保留旧数据路径直到其兼容测试通过。down 必须拒绝会丢失新权威生产记录的降级，不能假称所有新增语义均可被旧二进制读取；相应版本回退限制在 SP-T001 固定并经 SP-T007 演练。

数据、API、源码、生成物和 UI 改动按任务所有权提交评审。只因真实路径需要而清理代码，不进行无关命名、依赖升级或目录重排。任务影响：全部任务。

## 6. 工期估算

估算按当前工作区和 SP-T001 的单次实测校准，不是 Codex 官方速度指标或完成承诺。有效小时按连续执行的墙钟时间计算，包含 PM 预检、阅读、实现、运行测试、独立审查和直接相关返修；同一任务内重叠的基线命令不重复相加。不包含等待用户反馈、额度恢复、外部服务或无人值守间隔。

| 任务 | 有效小时 | 主要不确定性 |
| --- | --- | --- |
| SP-T001 基线与详细契约 | 实测约 1.3，约 75 分钟 | 已获用户接受；精确阶段时间见证据 |
| SP-T002 来源版本集合 | 1.5–3 | 历史名称/成员、code/lineage revision、工件保留和旧数据兼容 |
| SP-T003 新建生产与恢复 | 2–4 | 新建/重引入、候选 primary、幂等、权限和跨对象事务 |
| SP-T004 治理发布与回滚 | 3–6 | 完整 validation attempt、原子发布、旧入口防绕过、多提案与缺席回滚 |
| SP-T005 内部 AI 生产 | 1–2 | 结构化输出持久化、人工修正、授权与模型异常 |
| SP-T006 桌面生产体验 | 2–4 | 真实状态接线、恢复交互、独立 harness 和视觉回归 |
| SP-T007 完整验收 | 2–4 | 隔离环境、长测、实际模型与兼容性问题 |
| 剩余实施合计 | 11.5–23 | 不含已完成的 SP-T001；范围与环境不扩张 |

剩余实施加入约 20% 跨任务联调与额外返修缓冲后，为 **约 14–28 个有效小时**；连同已完成的 SP-T001，整项重构暂按 **约 15–30 个有效小时**，折合约 2–4 个八小时工作日。日历时间取决于逐项验收、额度和实际模型配置，不据此承诺某天完成或无人值守自动推进。

实测依据：[SP-T001 交付](../../evidence/SP-T001/summary.md)。首个 worker 33 分 06 秒，返修 worker 20 分 58 秒；独立首审 4 分 32 秒、复核 1 分 33 秒。基线命令 2 分 36 秒且与契约工作重叠，未暴露应用基线失败。独立评审发现并收敛四项实质契约缺口，说明审查和返修不可从估算剔除。该结果支持复用现有基础设施和缩短启动开销，但不把“文档/静态测试耗时比例”线性套用到数据库竞争、发布和浏览器任务。

SP-T003 的候选到新资产草稿可演示点，剩余约 3.5–7 小时，不含通用缓冲；可演示不等于已发布或 AI 已验证。SP-T004 后的后台生产检查点剩余约 6.5–13 小时。两者都需要前置任务逐项接受。

置信度仍为中低：T001 只实测了设计、基线和静态验证，尚无新事务实现的速度样本。SP-T002 保存真实实现/测试/评审时间，SP-T003 完成后再校准余量。后续 packet Ready 前核对 TypeID、工件保留、validation attempt 和生成输出存储等必要文件归属，见 [交接核对](../../evidence/SP-T001/handoff.md)。发现额外基础故障或范围变化时单列影响，不降低验证门槛。

## 7. 验证与环境

使用现有 Go、pnpm、sqlc、OpenAPI 生成和测试工具链。新增契约先放入规格目录，通过仓库已锁定的 OpenAPI/JSON Schema 校验库验证；对应任务实现时才修改规范 API 与生成物。

仓库 `make check` 包含启动/停止默认 Compose 的 smoke、安全镜像构建和生成物检查；默认 Compose project 为 `semlia-local`，镜像使用固定标签。最终验收必须在专用检出与专用环境中运行；SP-T007 执行前写明确切命令与资源归属，包括镜像标签。独立目录或 project 不自动隔离全局镜像标签，共享标签冲突时使用独立 Docker 环境。不能在当前默认栈上盲目运行，也不能将未运行的门禁标为通过。

每项任务有 RED/GREEN/REFACTOR、定向测试与相应契约检查。最后执行全量源代码门禁、10,000 资产基准、发布消费兼容性和两个桌面尺寸的真实流程。已有目录基准要求首页 p95 ≤150ms、精确地址搜索 p95 ≤250ms，并记录实际硬件与数据规模，不用前端 mock 性能代替。
