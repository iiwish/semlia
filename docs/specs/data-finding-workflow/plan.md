## 1. 决策摘要

本计划只描述后续外部接入工作。当前主线是 [语义生产闭环重构](../semantic-production/product-design.md)，其首次生产、发布和恢复不依赖 EAI-T001 至 EAI-T003。生产验收后须由用户另行确认恢复接入，再重新核对下述代码基线与缺口，不能直接沿用重构前的静态结论。

先证明普通外部客户端能正确使用已有公开契约，再设计真实缺口。当前执行候选范围仅包括消费基线、参考接入包、只读探索详细契约；不把完整产品验收表一次拆成全面开发项目。

| 批次 | 交付 | 不承诺什么 | 退出条件 |
| --- | --- | --- | --- |
| R0 公开消费验证 | 现有 REST/MCP/CLI/SDK 的新鲜一致性证据，以及无特权参考接入包 | 不证明未治理来源探索、完整业务映射或数字交付 | EAI-T001、EAI-T002 验收通过，协议证据与真实 AI 使用证据分开 |
| R1 只读探索契约 | 无已发布语义时的接入方式，物理对象与证据的最小授权投影、快照及拒绝契约 | 本计划不实施新凭据、新接口或数据库迁移 | EAI-T003 形成完整技术契约与实施范围，并单独提交审核 |
| R2 治理反馈与完整调研 | 候选提交、业务规则与映射验证、纠正后重检 | 不在当前工作图内，不能用 R0/R1 完成代替 | R1 验收后按实际缺口另行规划 |

R0 可以独立提供价值：明确接口能做什么、怎样接入、哪些拒绝必须保留。R1 的技术契约是安全边界设计，不是另建 AI 平台。生产执行属于已有可选领域能力，其新增业务验收不进入本轮范围。

## 3. 技术决策

### TD-001 保留既有服务边界

R0 不增加核心服务、数据库表、消息队列或新的 Agent 框架。REST 与 MCP 继续调用同一 distribution 应用服务，CLI 与 SDK 保留现有通道归因。外部任务、会话、整体预算与成果留在接入方。

替代方案是直接扩建 Web Ask 或业务任务表。拒绝该方案，因为它不能证明外部接入可用，并扩大产品和持久化范围。

### TD-002 分开测试设置、普通客户端与验证器

隔离测试设置负责创建合成工作区、已发布资产、消费者、固定 release binding 和最小机器凭据。普通客户端只接收 endpoint、workspace、凭据和业务案例，通过公开网络接口交互；测试设置的数据库与管理动作不计入客户端工作。

验证器可使用固定黄金答案检查公开输出，不能把黄金选表结果注入 AI 输入。凭据不出现在命令行位置参数、报告、Skill 或样本文件中。参考客户端不读取应用配置密钥、控制面数据库或内部应用服务。

### TD-003 协议探针不冒充 AI

参考包位于 `examples/external-ai/`，包含简单 Go 协议探针、案例与评分契约、Skill 和接入说明。探针复用仓库锁定的官方 MCP Go SDK及标准 HTTP 客户端，不引入新运行时或模型供应商依赖。

探针验证结构化调用与返回，不承接自然语言推理。真实 AI 验证由可用外部宿主加载同一 Skill 并使用相同机器契约完成；记录宿主、模型、Skill、案例和语义版本。没有可用宿主时如实记录该项未验证，不用探针通过代替 AI 通过，也不为此自建聊天服务。

不加载 Skill 的客户端仍受相同服务端门禁约束；Skill 改变工作方法，不改变工具能力和授权。参考包不保存业务任务数据库。

### TD-004 R0 消费边界保持不变

R0 凭据使用既有 `asset.read` 与 `semantic.resolve`，不含 `semantic.execute`、写入、审核、来源管理或发布权限。测试需要固定 release 时使用真实的 pinned binding，不创建假的发布状态。

对 `semantic_search`、`semantic_describe`、`semantic_resolve`、`semantic_plan`、`semantic_query` 和 `semlia://contract` 进行验证。解析调用可以写入其既有解析、验证和审计记录；“只读消费”指不写业务源数据、语义定义或发布状态，不宣称完全没有控制面写入。

### TD-005 探索需要独立能力契约

R1 的目标不是把管理路由整体放行，而是只读、来源限定、版本化的公共投影。最小动作集覆盖物理对象搜索、指定 revision 的对象详情，以及已关联证据的安全读取。现有已发布定义继续走消费契约，不把探索响应标成 released。

探索接口不触发扫描、不上传文件、不创建资产、不提交提案、不执行查询。需要刷新时返回扫描新鲜度与限制，由有权主体使用既有接入流程处理。对象正文中的指令作为不可信数据处理。

R1 详细契约必须比较两种凭据方案：扩展现有凭据类型并显式区分用途，或采用独立探索凭据投影。决策需要覆盖无 release 冷启动、consumer 归因、source scope、动作上限、撤销、轮换、兼容旧凭据与迁移回退。当前不选择“沿用消费权限但放开目录”的捷径，也不在契约完成前创建迁移。

### TD-006 快照先于探索读取

读取和分页须固定来源成员、dataset/field revision、名称、关系、证据与扫描覆盖，不能拼接最新指针形成历史响应。现有 schema 的版本化基础可复用，但成员关系与名称归属需要验证。

R1 契约必须覆盖未变化表复用旧 revision、字段改名、删除表、部分扫描、失败扫描和并发扫描。缺少可靠历史信息时返回不可验证或过期状态，不从当前值回填“历史事实”。允许后续新增快照成员记录或 revision 字段，但须说明权威、索引、迁移和保留策略；不创建调研任务表。

### TD-007 治理写入保持独立

候选反馈和提案属于 R2，不随探索权限开放。复用既有 Proposal、Validation、Review 与 Release，明确基础版本、幂等、当前主体授权和职责分离；不新建平行审批库。业务分类映射不能直接等同于 `PhysicalBinding`，必须有业务批准、适用范围、覆盖与冲突语义。

### TD-008 合同与失败优先

客户端只使用真实能力声明，不根据 Skill 推测尚未注册的工具。限额、权限、版本与结构错误使用可观察结果，正常 no-match 不泄露无权对象存在性，也不能解释成企业全库不存在。

客户端每次调用设定超时与预算，最多两次受约束重试；只对明确可重试错误重试，遵守 `Retry-After`。超时、未解析或拒绝不自动改写请求为更宽范围。整体取消只停止新调用，已发生的领域动作通过权威标识核实。

## 4. R0 基线与验证范围

| ID | 用例 | 观察点 |
| --- | --- | --- |
| B-01 | 契约资源和工具发现 | 确认 release-only 与执行配置；消费凭据不会因工具存在而获得执行权 |
| B-02 | 已发布搜索、描述、解析 | REST/MCP 的关键定义、版本、计划摘要及拒绝一致；CLI/SDK 复用已有一致性覆盖 |
| B-03 | 无匹配和歧义 | 返回规范拒绝或待澄清；不生成自由 SQL，不推断全库不存在 |
| B-04 | query/plan 标识读取 | 只读取当前身份仍获授权的版本，不泄露私有执行定位 |
| B-05 | 重试和幂等 | 同一请求重放不产生不同事实；不同通道的 ID、时间和 channel 允许按契约不同 |
| B-06 | 轮换、撤销与授权变更 | 下一次请求重新鉴权，已建立 MCP 会话不能缓存旧权限 |
| B-07 | 跨租户、伪造 release、混合认证 | 规范拒绝；不能用身份头、cookie 或已知对象 ID 越权 |
| B-08 | 无探索/提案能力与模型故障 | 明确缺口、停止或受限交付，不改用管理端或合成成功结果 |

预算/实际的 R0 案例只使用已发布的合成定义，验证候选比较、引用和正确识别能力缺口。需要物理探索、完整证据或新规则的案例以 `blocked_by_capability` 记录，不算完整调研通过。

## 5. 参考包输入与证据

参考包格式在 EAI-T002 中定义为版本化 JSON Schema，不成为产品领域模型。严格拒绝未知配置键和凭据嵌入。

| 对象 | 最小内容 | 保存约束 |
| --- | --- | --- |
| 案例输入 | 案例 ID、自然语言目标、约定交付类型、合成身份说明、可用能力与预算 | 不向 AI 暴露黄金答案，真实案例不进入仓库 |
| 评分 oracle | 允许/排除候选、必须引用的版本、预期拒绝、必需检查和能力缺口 | 与 Agent 可读材料隔离 |
| 调用证据 | 工具或公开路径、请求摘要、trace、版本引用、outcome、错误码、耗时 | 不保存 token、原始完整 Prompt、隐藏推理或事实明细 |
| 运行结果 | `passed`、`failed`、`blocked_by_capability`、`cancelled`；协议/AI 运行种类、版本、纠正与限制 | 受阻与取消不计成功；不用一个布尔值合并全部 AC |

初始本地案例预算：单次网络调用 15 秒、单案例 120 秒、最多 20 次工具调用，重试计入总数。这是待审测试配置，不是生产 SLA。需模型调用时先明确其费用上限；未配置限额不自动运行付费模型。

## 8. 验证与环境

既有轻量入口：`make test-contracts`、`make test-repository`、`make contracts-check`；应用包测试按任务精确选择，不以全量 `make check` 代替针对性断言。

现有机器接口集成测试：

```sh
go test -count=1 -timeout=10m ./tests/integration/db -run '^TestMachineCredentialLifecycleAndChannelParity$'
go test -count=1 ./cmd/semlia ./internal/platform/http ./internal/application/identity ./internal/application/distribution
```

`tests/integration/db` 的 TestMain 启动本机独立 Testcontainers PostgreSQL，`resetSchema` 会对该测试库执行 down/up。只能使用该隔离环境，不能改接共享、开发或客户数据库；测试容器失败不能通过跳过断言制造通过。该流程不涉及 deployment 服务器，不适用部署授权。

R0 集成测试设置会写隔离合成数据库并签发合成凭据，普通客户端保持消费权限。执行前复核 Docker、锁定工具链、空闲资源与当前 checkout，不从 HEAD 新建 worktree 后假设其中包含尚未提交的机器接口实现。

## 9. 风险与控制

| 风险 | 控制 |
| --- | --- |
| 脏工作区含本计划依赖的未提交实现 | 首任务记录 exact checkout、diff 摘要和未跟踪依赖；不 reset、不擅自 cherry-pick 或遗漏代码创建隔离分支 |
| 既有测试通过被当作外部 AI 可用 | 协议、真实宿主、知识覆盖与业务价值分开验收 |
| 测试中的管理操作进入参考客户端 | 独立设置与 oracle，检查运行时 import、网络路径和配置 |
| 为探索放宽现有凭据或 release-only | R1 先解决凭据用途与版本投影；无审核不改 action 白名单 |
| 当前名称或最新指针污染历史证据 | 改名、删除、未变化成员和并发扫描成为 R1 必测反例 |
| 文档或证据含指令与敏感定位符 | 输入视为数据，响应字段白名单，凭据与敏感内容不落评测报告 |

## 10. 实施闸门

本计划及 [任务图](tasks.md) 排期为 Deferred，均未获执行许可。语义生产闭环验收后，由用户明确恢复接入优先级；重新核对当前代码、计划、任务图和检查材料并获得确认后，才为 EAI-T001 生成受限执行包。每次只执行一个任务，未通过的基线先形成真实失败证据，不夹带服务端修复。

EAI-T003 输出的探索契约需独立确认后才进入其实现规划。当前不创建新 API、不迁移数据库、不部署、不运行真实查询，也不宣称完整调研能力已交付。
