# 数据资产、本体与血缘

状态：五类知识模型的产品设计依据。业务对象、业务口径、指标、数据资产和分析模型通过可寻址成员与版本化实现契约协同。完整生产契约和消费能力待实现与验收，本文不授权应用改码、数据迁移或部署。

## 1. 对象与边界

| 对象 | 职责 | 边界 |
| --- | --- | --- |
| 来源结构 | 保存原始表、视图、字段、类型、约束和来源版本 | 接入成功不等于业务含义已确认 |
| 业务对象 | 定义客户、订单的身份、粒度、属性和业务关系 | 自身有定义，不额外创建同名概念 |
| 业务口径与指标 | 保存术语/判定规则，以及基础/派生计算 | 不复制底层表字段，不自由猜测实现 |
| 数据资产 | 说明一份数据的用途、覆盖、结构、粒度、时间、质量与使用契约 | 引用来源及加工实现，不复制事实明细 |
| 映射与关联记录 | 独立保存成员绑定、身份对应和获准连接契约 | 可独立验证发布，不因同名或存在外键就认定业务含义 |
| 分析模型 | 引用常用资产、映射和关联，固定场景与默认值 | 不独占关系，不是所有查询的硬前提 |
| 临时查询计划 | 按本次问题组合获准知识和实现 | 不是正式模型，不自动发布为知识 |

属性、条件表达式、聚合与派生计算具有不同的结构化契约。属性归属于业务对象或事件，以资产 ID、revision 和成员 ID 寻址；字段归属于数据资产及来源结构。名字相同不证明身份或含义相同。

## 2. 原始表到数据资产

`user_info` 可能记录账号、客户、员工或混合对象。名称、中文翻译、同名字段和相似度只形成候选线索，不能证明含义或关联成立。AI 可基于注释、DDL、SQL、血缘、业务资料与授权验证提出候选，由业务和数据负责人确认。

| 必要信息 | 设计要求 |
| --- | --- |
| 身份与用途 | 稳定资产 ID、名称、业务域、用途与不适用场景 |
| 来源与成员 | 来源 revision、数据集/视图、可寻址字段、类型投影和业务解释 |
| 覆盖与粒度 | 业务覆盖范围、每行含义、对象键与约束依据 |
| 时间 | 事件时间、快照时间、时区、更新频率与有效范围 |
| 使用规则 | 包含/排除、编码、空值、去重和身份映射要求 |
| 实现 | 获准的来源、加工工件、视图或表达式引用，必要过滤与连接契约 |
| 质量与责任 | 负责人、验证结果、已知缺口、敏感级别与发布版本 |

来源字段名、类型和约束保留在原始观察版本，资产通过引用展示这些信息并补充业务义，不维护第二套来源事实。字段是资产成员，不要求每个字段成为一级知识。未确认含义保存为显式草稿。

语义整理不代替数据加工。去重、纠错、身份合并必须有已实现且经验证的逻辑；仅记录“需要去重”不能宣称已去重。首期复用既有数仓或受控视图，不隐含重建通用 ETL。

## 3. 多张客户表与映射归属

以下是说明性例子，不是真实库调查结果。

| 数据资产 | 粒度与用途 | 使用限制 |
| --- | --- | --- |
| 电商注册账号 | 一行一个账号，用于账号分析 | 账号 ID 不直接等于统一客户 ID |
| 统一客户档案 | 一行一个统一客户，提供当前区域等属性 | 需核对身份映射、唯一性与覆盖范围 |
| 客户每日快照 | 一行一个客户某一天的状态 | 必须明确快照日期，不能只按客户 ID 随意关联 |

不同含义的表分别整理为资产；多表共同实现一份资产时，必须有清楚的加工或视图契约。接入范围和执行范围分开：可按授权调查 ADS、DWS、DWD、DIM 等来源，正式计算只使用符合当前问题要求的已发布实现，不以层级前缀代替验证。

### 3.1 引用与选表的记录位置

| 位置 | 保存什么 | 客单价例子 |
| --- | --- | --- |
| 业务对象及属性 | 对象身份、成员含义、类型、历史策略 | 客户当前区域、首次有效支付日期；订单实付金额、支付时间 |
| 业务口径 | 定义和判定规则、对象/成员引用、参数 | 老客户引用客户首次支付日期；具体起点来自查询 |
| 指标 | 属性或指标依赖、聚合/公式、过滤、时间与单位 | 实付总金额、有效订单数为基础指标，客单价引用二者 |
| 分析模型实现 | 场景、粒度、默认值、资产与独立绑定/关联的版本引用 | 复用订单与客户的组合，服务多种分析问题 |
| 成员与物理绑定 | 独立记录：对象 revision/成员到资产 revision/成员，再到来源 revision/字段或表达式 | 客户首次支付日期落实到获准客户档案成员及其来源字段 |
| 关联契约 | 独立记录：身份、键、连接方式、基数、时间、必要过滤和验证依据 | 订单到客户的统一身份多对一关联 |
| 数据资产实现 | 实际数据集、字段及必要加工引用 | 真实表名和字段名由所引来源版本解析 |
| 临时查询计划 | 必要的知识、绑定、关系、来源、参数及可选模型引用 | 本次上月华东老客户的筛选与计算，不默认新建模型 |

绑定和关联只维护一份，知识详情、模型和查询上下文按引用组合展示。它们是可独立验证发布的实现记录，包含工作区、ID、不可变修订、范围、责任人、证据和验证状态，不增加面向用户的第六种知识类型。业务口径不保存所有候选客户表的 ID；模型或临时计划按需求选择获准绑定。计划固定知识、成员、数据资产、绑定、关联及来源版本，必须属于一致的 release；模型引用可为空。

换来源不必改写业务含义，但需要重新验证身份、粒度、字段含义、时间、质量和权限是否等价。成员 ID 或表名前缀稳定不证明绑定仍有效。多个兼容实现没有明确选择策略时，先澄清或阻断。

### 3.2 从业务问题到 SQL

以“上个月华东地区老客户的客单价”为例，整个问题共同约束取数：

1. 定位业务域内的客单价指标，直接读取它自身的定义；本例以订单数作分母，真实企业口径须确认。
2. 展开实付总金额和有效订单数两个基础指标，加载订单属性、客户属性、有效订单和老客户口径。识别属性类型、聚合阶段和参数。
3. 优先按指标 ID 与经验证的能力索引查找适用模型；没有适用模型但所需映射与关联已发布且允许组合时，按业务成员引用检索绑定并规划必要关联路径。所有候选都按完整需求检查，不能按模型或表名称猜测。
4. 沿模型引用或临时计划选定的独立绑定、数据资产和来源引用确定真实表、字段和表达式；使用获准键、粒度及 JoinContract。依据缺失、歧义或策略禁止时提出候选或澄清，不直接执行。
5. 形成明确版本的解析计划，交由受控执行适配器编译 SQL 和参数。规则缺失、类型冲突、歧义或不支持的聚合条件不得临时猜补。
6. 检查权限、来源有效性、唯一键、连接扇出、参数、预算及同范围计算，通过门禁后只读执行并与人工基准对账。

| SQL 部分 | 对应知识与实现 |
| --- | --- |
| SELECT 的除法 | 客单价派生指标公式 |
| SUM / COUNT DISTINCT | 实付总金额和有效订单数基础指标，及订单键/粒度 |
| FROM / JOIN | 查询计划选定的数据资产和物理绑定，可来自模型复用或按需规划 |
| ON | 身份映射、对象键、连接基数与 JoinContract |
| 有效订单过滤 | 有效订单口径的已确认判定规则 |
| 支付时间与区域过滤 | 对象属性的时间/编码语义及成员绑定，问题提供参数 |
| 首次支付早于区间起点 | 老客户口径中的客户属性判定，不另建同名分群 |

知识保存公式、条件、参数定义、依赖与映射；取数计划、SQL 和具体参数属于本次消费产物，不要求预存每个问题的整段 SQL。历史 SQL、缓存和问答结果不自动成为权威知识，作为实现或修订证据时仍需确认与发布。

汇报 SQL 是手工编写的生成结果示意，不是原型执行结果。花括号表示未核实的真实绑定，字段是示例；不能把它当成可执行模板。标识符和表达式根据获准契约编译，参数由执行适配器绑定，不把用户文字直接拼接。

本例按支付时间和客户当前区域分析上月交易，首次有效支付早于上月起点；金额与订单数使用相同范围。区间按业务时区左闭右开，区域值按已确认编码映射。一行一笔订单、一行一客、目标范围内完整多对一关联和同币种金额均须验证。COUNT DISTINCT 不能修复金额扇出，空值、零分母、退款、身份缺失及时间边界必须明确。

查询审计以必要的版本、计划和执行归因为核心；敏感问题、SQL、参数与结果遵循权限、脱敏及保留策略，不默认记录完整原文或事实明细。

### 3.3 分析模型保存什么，如何生成

分析模型保存可复用的分析配置及引用，不保存客户或订单事实行，不独占映射和关联。名称“订单分析”是展示信息，不参与确定性匹配。指标公式、对象属性含义、业务口径判定和来源表结构分别由对应知识或来源版本管理，模型不复制它们。

| 模型信息 | 订单分析的说明性配置 | 匹配时用途 |
| --- | --- | --- |
| 场景与基础对象 | 有效订单分析，以订单为基础对象 | 核对业务域、覆盖范围、身份与基础粒度 |
| 能力索引引用 | 对应模型修订和 release 下经校验的指标、口径引用 | 按指标 ID 查找候选；不是手工枚举所有问题，也不直接授权执行 |
| 公开属性与时间角色 | 订单支付时间、客户当前区域 | 核对查询要求的时间、分组和筛选含义 |
| 场景约束 | 有效订单范围、客户当前属性、公开成员限制 | 校验规则能力、参数、求值阶段和必需成员，不隐式覆盖业务定义 |
| 数据实现 | 订单交易数据与统一客户档案的版本引用 | 确定实际数据覆盖，沿绑定解析字段与表达式 |
| 绑定与关联引用 | 独立记录的 ID/revision，对象属性到资产成员、客户键、多对一连接 | 与临时计划复用同一份关系，不重复维护 |

模型形成由真实试点、常用报表或已有 SQL 的复用需求驱动：整理资产及独立映射/关联 → AI 提出组合草稿 → 负责人确认场景与实现 → 验证、独立审核与发布。接入两份资产不自动生成一个模型，不遍历全部资产组合或全量可能问题。未确认关系仍为候选，不能通过模型包装取得执行资格。

一份订单分析配置可服务总客单价、按区域拆分和老客户客单价。月份、地区或问法变化只产生查询参数和临时计划；历史区域、客户身份、粒度或政策有实质差异时才评估独立模型或实现。候选按业务范围、基础粒度、时间角色和版本化关系组合去重；重复使用、点击多数或 SQL 成功不自动发布模型。

发布校验可生成能力索引，记录可计算指标、可用口径、模型修订、release、所需依赖和验证依据。它是可重建的检索投影，不是另一份指标定义。新增指标依赖可由现有模型实现时，验证后更新发布范围内的索引，不复制模型。字段齐全仍需检查粒度、时间、过滤求值阶段、完整连接路径和执行能力；索引失效或版本变化时重建，运行时仍执行权限与有效性检查。

新增或变更知识依赖使用包含相应修订的新 release，再生成该 release 的索引；旧 release 不可变，不向历史发布中补入新能力。模型配置未变化时可以复用原模型修订。

### 3.4 模型复用、按需规划与缺口处理

| 条件 | 路径 | 产物 |
| --- | --- | --- |
| 有适用且获准的模型 | 优先复用模型，展开其引用的获准记录 | 引用模型版本的查询计划 |
| 无适用模型，完整依据已发布且策略允许组合 | LLM 按稳定业务成员 ID 检索绑定，在获准关联图中有界规划 | `modelRef` 为空的临时查询计划，不创建知识 |
| 含义或关系未知、实现缺失、权限或策略不满足 | 明确缺口、澄清或提出候选；授权验证单独进行 | 待确认任务，不直接取数 |

两条可用路径均以整个问题的需求为约束。客单价引入金额与订单身份；区域和老客户引入客户当前区域及全历史首次支付属性。由成员绑定定位订单交易数据和统一客户档案，由获准 JoinContract 连接两侧。只支持日汇总客单价但缺少客户身份的实现不能执行老客户筛选。已治理宽表若语义等价并有完整绑定，可采用单表计划。

模型检索可使用能力索引；无模型路径以业务成员到已发布绑定的索引和可独立发布的关联契约为依据。对候选资产数、跳数、规划耗时与执行预算设置边界，优先最少必要数据，预算用尽返回缺口而不是降低验证要求。多个非等价实现需要澄清或已确认场景策略，不能用向量分数、最短路径或多数历史选择决定含义。

无模型路径不能作为策略绕行：模型因权限、强制场景规则或业务冲突被拒绝时，不允许借临时计划访问同一受限数据。若场景规定必须使用特定模型，临时规划也受此约束。缺少模型默认时间时必须从已确认指标/口径或本次澄清取得时间含义，不凭空继承默认值。

临时计划固定 release、业务需求、数据资产、来源、绑定、关联、参数和可选模型版本，记录必要的选择与校验依据。知识发布不冻结实际数据；执行和对账仍记录数据时间或快照。计划不属于正式知识，按审计与保留策略保存，不默认收集敏感原文或结果。

### 3.5 LLM 与执行边界

LLM 可以提出临时计划、关系候选和建模草稿，在单独授权范围内申请只读数据验证；它不能凭同名字段、自行推断或一轮 SQL 成功就确立权威关系，也不能发布或扩大权限。候选关系经业务/数据确认、验证、独立审核与发布后，才能进入正式取数所用的关联集合。

受控解析器校验引用、类型、范围、参数和版本；执行适配器编译标识符与表达式并绑定参数。两条可用路径都检查业务口径、身份与键、时间覆盖、空值与编码、连接方式、必要过滤、整条路径基数与扇出、只读权限、成本及超时。单条关系通过验证不代表组合路径一定正确，COUNT DISTINCT 不能修复金额扇出。

来源变更、知识或关系撤销、权限变化及过期验证必须使受影响的索引与待执行计划失效或重验。模型复用与按需规划按相同范围和数据快照对账；没有独立记录发布或临时规划执行能力时，产品应明确显示该路径未就绪，不以演示图冒充实现。

完整目标结构见[定义示例](knowledge-definition-examples.json)中的 `analysis_model`、`reusableImplementationExamples`、`capabilityIndexExamples` 和 `queryPlanExamples`。示例均为草稿或说明性计划，来源及依赖未完整展开，不可用于真实发布取数。

从原始材料到知识发布，再到整句需求解析、SQL 和合成结果演算的完整案例，见[老客户客单价的知识加工与消费](case-walkthrough.md)。

## 4. 本体设计

本体组织业务对象、可寻址属性、口径、指标及其有类型关系和约束，不是五个目录标签或一种存储技术。对象自身具有定义，业务口径与自己的判定规则一起版本化；业务事实行留在数据源。

| 关系平面 | 示例 | 约束 |
| --- | --- | --- |
| 成员归属 | 客户拥有首次有效支付日期属性 | 成员身份明确，对象粒度与时间语义一致 |
| 业务关系 | 订单属于客户 | 声明方向及业务基数，不直接授权物理 Join |
| 规则依赖 | 老客户口径引用客户首次支付日期 | 定义与判定规则一致，日期参数及空值处理明确 |
| 计算依赖 | 客单价引用实付总金额、有效订单数 | 依赖无环、同范围、单位与聚合阶段兼容 |
| 实现映射 | 客户属性映射统一客户档案成员 | 固定双方修订、来源、范围与验证结果 |

关系保留类型、方向、端点资产/成员、版本、适用范围、来源证据和断言状态。候选或推断关系只供调查，不进入生产默认解析。模型、知识与实现由 release 固定兼容组合，不把层级或普通关联中的所有环都当作计算循环；依赖无环约束适用于计算图。

首期不宣称完整 OWL 推理能力，不将未知自动判为否定。本体可以采用已有的关系存储，不以形式推理引擎为前置条件。

## 5. 血缘与影响分析

数据血缘接入属于后续建设范围，当前尚未具备。规划将其作为知识加工的补充输入，辅助区分候选表、核对派生字段来源与加工过程，并支持变更影响分析。缺少血缘时可基于数据库结构、已有 SQL 和业务文档整理草稿；血缘本身不证明业务含义，证据不足的映射仍需补充验证与确认。

数据血缘、语义依赖和证据溯源分别记录，通过版本化映射连通。

| 视图 | 回答的问题 | 示例 |
| --- | --- | --- |
| 数据血缘 | 字段由哪些输入及处理产生 | 支付记录经有效支付筛选和客户级最早时间聚合，得到首次支付日期 |
| 语义依赖 | 哪些规则和计算使用该成员 | 客户首次支付日期属性被老客户口径引用，使用该口径的指标/模型受影响 |
| 证据溯源 | 为什么接受定义与映射 | 口径文档、代码 revision、人工确认和验证运行 |

客单价指标不永久绑定老客户范围；本次查询把老客户口径应用于同范围的基础指标。专门发布的“老客户客单价”可以显式固定口径。影响分析区分永久定义依赖与本次查询使用记录，不能把一次使用写成所有客单价的长期依赖。

首轮追踪选定案例的数据集级和关键字段血缘。静态解析、实际运行观察、人工确认与未解析部分明确区分；没有运行事件不能宣称加工已成功。每条记录至少包含上下游、转换工件、方向、来源版本、观察时间、有效范围、证据和状态。不承诺动态 SQL、存储过程或全库列级血缘均可自动解析。

来源或成员变化沿血缘、绑定及语义依赖定位待重验对象；不能通过影响查询暴露未授权知识或字段。

## 6. 存储选择

首轮以 PostgreSQL 保存有类型、带版本的资产、成员、关系和绑定，用索引与有界递归查询支持局部关系及影响追踪。源明细留在数据源，图形展示不决定存储技术。

只有复杂多跳或图算法成为真实核心负载，且经过索引、权限过滤及查询优化后仍达不到约定时延，才评估图引擎；需比较规模、并发、同步延迟、运维与授权一致性。需要时优先采用可重建的查询投影，避免双主数据。

## 7. 实现与验收边界

类型专属结构、独立映射/关联发布、模型能力索引、无模型规划与真实取数分别验收；知识类型入口存在不代表完整消费能力可用。工作树接口与兼容要求见[知识类型 §5](knowledge-types.md#5-当前接口覆盖与兼容要求)。不按名称自动合并现有知识，不删除旧 ID 或改写历史 release。

验收至少包括：

1. 同名客户来源、账号与客户身份、快照粒度不自动归并；数据资产必要规则未知时不能发布为可执行。
2. 对象、属性、口径、指标及实现用 ID/revision/成员引用；业务对象和指标自身的定义无需重复概念。
3. 老客户定义与判定同版本；月份是参数，未知首次支付不自动匹配；无执行规则时只解释不取数。
4. 原始金额、SUM/COUNT 和派生除法明确区分，行级 WHERE 与聚合判定不混用。
5. 只更换物理实现时业务定义保持稳定，成员、身份、时间、连接、权限与结果必须重验。
6. 沿关键字段血缘和成员依赖找到受影响口径、指标与模型，未知范围及权限限制可见。
7. API、存储、编辑器、验证、发布与消费一致，旧身份和历史引用可追溯；真实 SQL 结果通过对账。
8. 无模型但获准依据完整时生成临时计划，与模型路径同快照对账；缺少关系、扇出、过期版本及权限/政策冲突都阻断。
9. 相同资产和关系支持多个问题，不因参数变化、反馈重复或 SQL 成功创建或发布模型；有明确复用价值的草稿仍经过独立审核。

## 8. 对话反馈、用户偏好与通用知识

用户对话中的选择、纠正和补充说明，按适用范围进入用户偏好或系统通用知识两条沉淀路径。用户偏好影响为该用户组织回答的方式；通用知识完善经确认的业务定义、数据含义、映射和关联。这是使用范围与治理方式的划分，不增加两种一级业务知识类型，也不等于物理清洗或自动训练模型。

### 8.1 分流与生效范围

| 路径 | 对话例子 | 保存位置与范围 | 生效条件 |
| --- | --- | --- | --- |
| 用户偏好 | “以后先给结论，再给表格。” | 当前工作区内该用户的个性化配置，不进入共享业务知识目录 | 用户明确要求记住或确认后，按允许的配置项生效；可查看、修改、删除与停用 |
| 系统通用知识 | “经营分析中的销售额，不包含集团内部交易。” | 销售额统计口径的修订候选，关联具体指标与场景；发布后限获准业务域、工作区与用户复用 | 确认业务规则与适用范围，核对版本、内部交易识别方式与样例结果，独立审核与发布 |

同一段对话可包含多个陈述，分别分类并关联必要的来源依据，不强制整段只属于一条路径。无法确定类别或有冲突时保留待确认项；没有长期价值的内容不保存。“本次按客户当前区域看华东交易”仅确定本次参数或语义选择，不自动形成长期偏好，更不成为全局口径。

“系统通用”不表示对所有用户公开或跨租户共享。个人对话不能直接复制到共享知识库；进入通用候选前检查共享授权、敏感信息、原文范围和证据访问权限。用户身份、私有偏好和不必要的对话内容不随业务事实传播。

### 8.2 用户偏好管理

偏好以有类型的允许项保存，例如回答语言、详略、先结论后明细、图表展示形式；不是一段可以覆盖系统行为的任意提示词。仅根据行为推测的偏好保持候选状态，不能由一次点击或模型置信度直接变为长期设置。

每条记录包含稳定 ID、工作区与用户身份、偏好键和值、适用场景、必要来源引用、用户确认状态、更新时间、有效期或停用状态。读取、更新与删除按用户隔离；过期、撤回或删除后不继续应用。保留记录需最小化，默认不保存完整对话或敏感明细。

在展示类配置上，本次明确要求优先于已确认的个人偏好，个人偏好优先于产品默认值；授权、业务口径和强制规则始终独立生效。会影响取数含义的时间角色、客户范围或数据实现选择，必须来自可用的已发布定义与授权配置，并展示采用依据；存在歧义时澄清，不作为普通展示偏好绕过确认。偏好不能把缺少实现的查询变成可执行，也不能关闭审核或扩大访问范围。

### 8.3 使用时澄清

候选展示业务含义、数据粒度、覆盖范围、来源版本、确认状态和已知限制，不要求普通用户仅凭表名选择。没有依据的解释必须标为候选，不把 AI 编造的中文名称当成事实。选项包含“都不是”“不确定”，允许补充理由和纠正已有选择。

例如“本月客户数”可澄清为注册账号数或统一客户数。用户选择仅证明其本次意图，不证明原始 `user_info` 表必然表示账号，也不证明账号 ID 唯一。已存在适用、获授权的已发布实现时可按原有门禁取数；仅有未知候选或未验证映射时仍需等待确认或拒绝计算。选择行为不扩大读取、执行、审核或发布权限。

### 8.4 通用知识候选与证据

通用候选由有共享授权的业务纠正或补充材料形成，仍归入五类业务知识或独立映射/关联记录。陈述本身不是事实证明。例如“经营分析中的销售额不包含集团内部交易”补充了统计范围：数据库可能记录交易对手或内部交易标识，但是否排除这类交易不能由表结构单独决定。该例仅作说明，不代表企业现行口径。发布前须由业务负责人确认规则依据、适用场景和有效期，关联具体指标与版本，由数据负责人核实内部交易识别条件并对账；存在冲突时保留待确认状态，不能直接改写既有口径或本次 SQL。

反馈记录至少保存可去重的事件身份、工作区、授权主体或受控主体标识、问题/意图、业务场景、统计时点、候选集合与对象版本、所选项或放弃原因、可选理由、发生时间，以及可取得的结果核对或后续纠正。问题与理由按敏感级别最小化保存和脱敏，设置保留期限，不默认收集业务明细或交给外部模型。

反馈关联候选或已有资产，不直接覆盖资产定义。用户可撤回或纠正；修订候选保留反馈来源，发布后也能定位由哪些证据支持。历史选择对其原始版本有效，不静默迁移到含义变化后的来源或知识版本。

### 8.5 通用知识整理与发布

首轮支持人工触发的有界批次；后续周期任务在配置的授权范围内按场景、业务含义和版本聚合，去除重复事件、标记异常与矛盾，生成定义、别名、适用范围或映射的修订候选。反馈频率用于发现待处理问题，不能直接作为正确性、权威性或发布资格；同一个人重复点击不等于多个独立证据。

反馈文本是待分析数据，不是系统指令，不能改变权限、跳过验证或指定发布动作。冲突、跨场景选择和低证据反馈进入人工确认，不按多数票合并互斥定义。业务负责人确认语义，数据负责人验证表字段与执行逻辑，独立审核沿用既有职责分离。

整理任务只产出候选，记录输入窗口、来源版本、去重标识、处理状态和候选关联，保证重试不重复创建修订；无变化时不生成无意义候选。只有通过校验并发布的修订可供下一次生产使用。来源或规则变化后需重新验证；错误规则可沿既有版本机制纠正或回滚。

### 8.6 验收与效果

- 同一对话的偏好与业务纠正分别处理，本次意图不默认长期保存；未知分类进入确认，不强行归类。
- 只有用户明确要求记住或确认的允许项生效；偏好可修改、停用和删除，跨用户/工作区不可读取或应用。
- 本次展示要求覆盖既有展示偏好，但不能覆盖授权、强制规则或业务口径；取数语义歧义仍需澄清。
- 私有对话与偏好不直接进入通用知识；通用候选先做共享授权和敏感信息检查，再验证审核发布。
- 同一场景重复反馈不重复计权，不同场景不被合并成全局默认。
- 无权限候选不可见，选择未发布候选不触发越权或未验证查询。
- 定时/批次重试不产生重复提案，冲突反馈保留原始依据，不覆盖已发布版本。
- 用户撤回、来源变化和验证失败可定位受影响候选；只有适用且已发布规则被后续问题复用。
- 效果以同类问题的重复澄清率、结果核对准确性、修订采纳及错误撤回情况共同评估，不以点击量或“少问用户”单独证明改善。

这是目标机制，用户偏好管理、对话分流、通用候选整理及其生效与隔离契约均需实施验收，不表示已启用长期记忆、跨用户共享或任何运行中的定时任务。
