# 老客户客单价的知识加工与消费

本文用一个说明性问题贯通知识加工、发布、消费和反馈。五类知识及成员结构采用[知识对象契约](knowledge-types.md)，模型、绑定和权限采用[数据资产、本体与血缘](data-assets-ontology-lineage.md)的边界。本文为目标设计，合成演算不代表产品具备完整自动加工、选模或真实取数能力。

## 1. 问题与案例假设

问题：上个月，华东地区老客户的客单价是多少？

案例约定：

- 客单价采用同范围实付总金额除以有效订单去重数，单位为元/单。
- 时间采用订单支付时间，演算固定为 2026-08-01 至 2026-09-01，左闭右开。
- 区域采用客户当前归属，不用它代替交易发生时的历史区域。
- 老客户首次有效支付日期早于统计期起点，未知日期不自动匹配。
- 首次有效支付日期是客户粒度的全历史属性，不能从上月交易临时计算。
- 真实有效订单、退款、时区、区域编码、币种和身份映射须由负责人确认。

这个问题用于确定试点所需知识与验证范围。知识与模型可以服务同一业务范围内的多种查询，不为每个问句重新创建。模型是常用配置；无适用模型但已有完整获准映射与关联时，允许形成临时查询计划，依据不足时进入验证流程。

## 2. 知识加工链路

| 阶段 | 输入 | 加工与确认 | 输出 |
| --- | --- | --- | --- |
| 来源辨认 | 获授权的表结构快照、业务文档、已有 SQL 和加工工件 | AI 提出含义与关联候选，负责人核对用途、粒度、身份、时间和覆盖 | 数据资产草稿、来源版本引用、待确认项 |
| 业务定义 | 资料中的术语、计算说明和经确认来源含义 | 定义对象及属性，将条件与公式转为类型明确的结构，保存依赖与证据 | 客户和订单对象、老客户和有效订单口径、基础与派生指标草稿 |
| 映射与关联 | 业务知识、数据资产与可用加工实现 | 数据负责人确认成员映射、身份、键、粒度、连接和范围，系统校验兼容性 | 可独立验证发布的成员绑定、PhysicalBinding 与 JoinContract 记录 |
| 模型沉淀（按需） | 试点、常用报表或已有 SQL 中的真实复用需求 | 引用已有映射与关联，确认场景、基础粒度、默认值和使用约束 | 可复用的分析模型草稿，不枚举所有分析组合 |
| 验证发布 | 相互兼容的定义、实现及来源证据 | 业务确认，系统与数据验证，独立审核并按权限发布 | 不可变发布 manifest、固定必需知识与实现版本；模型可选 |

### 2.1 辨认多份客户相关数据

以下原始名称及对应关系均为示例，不是数据库调查结论：

| 原始来源 | 核对重点 | 可形成的目标资产 |
| --- | --- | --- |
| `order_detail` | 是否一行一笔订单，金额、订单键和支付时间是否符合定义 | 订单交易数据 |
| `user_info` | 是否记录账号，账号 ID 与统一客户 ID 如何对应 | 电商注册账号数据 |
| `customer_base` | 统一客户键、当前区域、首次有效支付属性的来源和覆盖 | 统一客户档案 |
| `customer_daily` | 客户与日期的组合粒度、历史状态覆盖 | 客户每日快照 |

原始注释、查询代码、主外键和数据观察分别提供证据，不把名称翻译当作事实。来源层保存实际表字段与类型，数据资产引用来源版本并补充业务用途、字段含义和限制。

知识加工不等于事实数据加工。缺少去重、身份合并或历史首次支付计算时，需复用或实现经验证的仓库逻辑、受控视图或加工工件。仅写下加工要求不能让资产变成可执行。

### 2.2 形成结构化业务知识

业务对象管理客户和订单的自身定义、身份与属性。业务口径管理老客户定义及比较条件、适用对象、参数和空值策略。有效订单有独立的状态、退款及排除规则，不能从术语自动猜测。

实付总金额与有效订单数是基础指标，引用订单属性和有效订单口径；客单价是派生指标，引用两个基础指标。属性、行级判定、聚合与聚合后计算具有不同类型，不能把聚合条件直接拼成行级过滤。

每项关键结论保留材料版本、证据和确认记录。对象与指标自身包含定义，不额外生成同名口径。具体月份与区域值属于消费参数，不固定进这些全局定义。

### 2.3 独立映射、关联与按需模型

| 业务成员 | 数据资产实现 |
| --- | --- |
| 订单实付金额、订单键、支付时间 | 订单交易数据的相应成员 |
| 客户当前区域、首次有效支付日期 | 统一客户档案的相应成员 |
| 订单客户身份与客户身份 | 获准身份映射和多对一连接契约 |

成员引用固定资产 ID、revision ID 和成员 ID。成员绑定与关联契约是可独立验证、审核和发布的记录，模型及临时计划都引用其 ID/revision，不复制映射。底层绑定解析来源字段或表达式；关联契约约束键、身份、粒度、连接方式、必要过滤和时间范围。业务明细保留在来源。

订单含账号 ID 时必须先解决账号到统一客户的映射。客户快照按明确日期或有效期间连接，不能直接制造一对多扇出。已治理宽表若提供语义等价的全部属性，可以成为另一份适用实现；统一客户档案不是所有查询的固定必选表。

接入订单与客户资产不自动生成所有分析模型。真实场景需要反复按客户属性分析交易时，AI 可以提出“订单分析”草稿，引用这些独立记录并明确一行一笔订单、支付时间及客户当前属性等约束，经验证审核后发布。总体客单价、分区域客单价和老客户客单价复用同一模型；月份、区域值与口径组合不各建一份模型。

模型的能力索引由指定发布范围内的指标/口径依赖校验生成，用于检索候选。它不复制公式，也不因为列出客单价就证明本次全部需求可执行。新增指标能够复用现有绑定时，验证后更新索引，不复制模型。常用临时计划只有具备复用价值并通过确认、验证和独立审核，才成为正式模型。

### 2.4 加工交付与停止条件

发布版本固定对象及成员、口径和指标、资产、独立绑定、关联以及验证依据的兼容组合，可包含按需模型。发布不可变知识不等于冻结源数据，数据时间或快照仍需在执行与对账中记录。

缺少证据、业务含义冲突、无法解析成员、来源超出权限、键或粒度不成立、加工未实现、连接可能重复计数时，保留草稿与具体缺口，不以模型置信度或一次执行成功放行。修复形成新修订并重新验证，历史发布内容保持可追溯。

## 3. 知识消费链路

| 阶段 | 使用什么 | 产物 |
| --- | --- | --- |
| 解析整个问题 | 发布知识中的指标、属性、口径定义及本次问句 | 确定的知识 ID、订单侧和客户侧需求、时间及区域参数 |
| 选择规划路径 | 模型能力索引，或已发布成员绑定、关联契约、场景策略与权限 | 复用适用模型、无模型按需规划，或明确缺口 |
| 展开绑定 | 数据资产、独立成员映射、来源 revision 和连接契约 | 固定版本的临时计划与必要表字段、过滤和参数；模型引用可为空 |
| 编译与执行 | 计划及执行适配器能力 | 经验证、获授权的只读 SQL 执行与受限结果 |
| 返回与对账 | 结果、采用口径、知识版本和实际数据时间 | 可核对答案，或明确的失败、缺口及纠错入口 |

客单价引入订单金额与订单身份，指标时间定义引入支付时间。华东地区与老客户分别引入客户当前区域和首次有效支付日期，再通过客户身份把两侧需求关联起来。因此客户资产不是由客单价单独推出的。

指标 ID 可以作为模型能力索引的候选检索入口，但整句问题的全部需求共同约束可用实现。支持总体客单价的日汇总模型若缺少客户身份，就不能处理老客户筛选。多个适用实现按已确认场景策略选择，仍有含义差异时澄清。

| 情况 | 本例的处理 |
| --- | --- |
| 有适用的订单分析模型 | 复用其场景配置，展开订单与客户的独立绑定及关联引用 |
| 无适用模型，获准依据完整 | 按订单金额/身份/支付时间与客户区域/首次支付等成员 ID 检索绑定，在获准关联中组合相同两份资产，形成 `modelRef` 为空的临时计划 |
| 身份、映射或关联未知 | LLM 提出候选及验证需求，不能只凭同名 customer_id 直接关联；确认、验证、审核发布后才供正式取数 |

两条可用路径都检查整条计划的粒度、时间、必要过滤、身份、基数、覆盖、连接扇出、版本、只读权限和预算，并在执行前检查来源与发布状态。无模型路径不得绕过强制模型政策、权限或业务冲突；候选数量、跳数和规划耗时受控。字段齐全或单条关系有效不证明整体计划正确。

SQL 按本次计划生成。知识保存公式、判定与参数定义，模型保存实现引用；本次问题提供参数值。生成 SQL 不等于获准执行，仍需检查只读权限、预算、来源与版本、连接扇出和范围。

临时计划是一次消费产物，不写入正式知识目录。重复提问、换月份或地区只改变计划参数；执行成功和用户选择也不自动触发模型发布。需要长期复用的组合进入前述模型沉淀流程，按范围、粒度、时间与关系版本去重。

## 4. 合成结果演算

样本位于[case-example.json](../../briefings/2026-09-semantic-platform/case-example.json)，包括七笔订单和四位客户。订单事实与客户的全历史首次有效支付属性分别保存，按同一客户身份关联。

| 订单 | 金额 | 本次处理 |
| --- | --- | --- |
| O01 / C01 | 100 元 | 纳入 |
| O02 / C01 | 200 元 | 纳入 |
| O03 / C02 | 300 元 | 纳入 |
| O04 / C03 | 400 元 | 首次有效支付在八月，排除 |
| O05 / C04 | 500 元 | 当前区域为华南，排除 |
| O06 / C01 | 600 元 | 七月支付，排除 |
| O07 / C02 | 700 元 | 不符合样例有效订单标记，排除 |

本次金额为 600 元，有效订单为 3 笔，属于 2 位客户。客单价为 **600 ÷ 3 = 200 元/单**。样例使用 `is_valid` 标记仅为隔离演算方便，不能把它当成企业实际有效订单规则。

结果页展示演算与采用条件，不宣称执行了真实来源查询或验证了完整产品。真实验收需要使用相同数据快照或一致期间的人工基准，覆盖总量、分组和时间比较，并检查零分母、空值、无匹配身份、日期边界及连接重复。

## 5. 对话反馈的两条沉淀路径

仍以同一个问题为例：地区含义尚不明确时，展示客户当前区域与交易时区域的差异，用户澄清当前意图。前述演算采用当前区域，是该分支完成澄清后的假设。

仅本次有效的选择不默认长期保存。用户说“以后先给结论，再给表格”，可经明确记忆要求或确认后保存为当前工作区、当前用户的展示偏好，支持查看、修改和删除；不影响客单价公式、客户范围或数据权限。本次明确展示要求优先于已有展示偏好。

用户补充“经营分析中的销售额，不包含集团内部交易”，则在共享授权与敏感信息检查后形成销售额统计口径的修订候选，关联具体指标、场景与版本。业务负责人确认规则依据和适用范围，数据负责人核对内部交易的识别条件与样例结果，独立审核后发布。这类统计规则不能由数据库结构单独确定。该例为说明性假设，不代表企业现行口径，也不直接改变前述客单价定义或本次 SQL。

同一段对话中的偏好和业务纠正分别处理，分别保留必要依据。用户偏好属于个性化配置；系统通用知识仍归入五类业务知识及独立映射/关联记录，“通用”限获准业务范围，不默认跨用户暴露原始对话或跨租户共享。重复选择不能证明字段含义、身份或唯一性，也不自动覆盖全局口径。

通用候选经过业务确认、数据验证与独立审核发布后，才能供授权范围内的同类问题复用。缺少获准实现时不因用户点击或个人偏好而允许取数。源字段或规则变更沿血缘和依赖定位影响，进入同一修订与重验过程。具体分流、偏好隔离与撤回规则见[对话反馈设计](data-assets-ontology-lineage.md#8-对话反馈用户偏好与通用知识)。

## 6. 验收与实现边界

验收应逐步核对材料、结构化知识、成员绑定、发布包、需求解析、模型选择、SQL 和数值结果，而不是只检查页面或发布状态。详细测试范围见[端到端验收计划](end-to-end-acceptance-plan.md)。

模型复用与无模型规划应在相同快照上核对本例 600 ÷ 3 = 200 的结果；隔离测试中缺少关联、客户键重复、历史范围不满足、权限撤销与来源版本变化均须阻断或重验。查询参数变化不增加模型数量，候选不得自行发布。

类型结构入口与完整消费能力分别验收，实现边界见[知识对象契约 §5](knowledge-types.md#5-当前原型覆盖)。本文不修改发布权限，也不授权自动迁移和部署。
