# 业务词汇与问数检索效果对比

## 结论

在 V1 本地验收环境（合成数据、真实模型 deepseek-flash）中，给演示知识补上受治理的业务词汇后，口语化问题组从 **12/24** 提升到 **24/24**（8 道题 × 3 轮）。“销售额”这类有歧义的说法，从模型静默猜测变为服务端按区分说明澄清，并且不调用模型。原 4 道黄金题去掉“使用已发布分析模型 …”前缀后仍全部答对，结果与独立 SQL 一致。

这是一组固定的合成问题，规模很小，不代表任意业务问题的正确率。

## 方法

- 代码：P1 业务词汇契约与门禁、P2 问数卡片与确定性检索、P4 典型问题召回门禁。前后两次测量运行的是同一版代码，差别只在于是否发布了词汇。
- 词汇通过正常治理流程发布：作者修订 → 业务规则确认 → 生产校验（含别名冲突与典型问题召回）→ 独立审核 → 发布。三个操作依次是：
  1. 词汇：有效支付金额、有效订单数、客户（区域属性别名与取值别名），并新建易混淆指标“下单金额”。
  2. 派生：客单价、老客户，重新固定到新修订。
  3. 模型：重新固定分析模型的全部引用。
- 每道题以 consumer 身份提问；生成计划的题执行只读查询，并与独立 SQL 按列对账；预期澄清的题要求不产生计划，且澄清文本列出候选。
- 命令：`node scripts/acceptance/v1-model.mjs vocabulary-baseline | apply-vocabulary | vocabulary-measure`。原始台账写入受保护的 `.semlia/v1-acceptance/current/`，不入库。

## 结果

| 题目 | 问题 | 词汇前 | 词汇后 |
| --- | --- | --- | --- |
| 指标别名 | 2026年8月的GMV是多少？ | 0/3（澄清） | 3/3 |
| 取值别名 | 2026年8月江浙沪的成交额是多少？ | 0/3（澄清） | 3/3 |
| 口径别名 + 派生指标 | 2026年8月华东区回头客的客单价是多少？ | 0/3（澄清） | 3/3 |
| 指标别名（模型可推断） | 2026年8月的单量是多少？ | 3/3 | 3/3 |
| 属性别名（模型可推断） | 2026年8月按大区统计成交额。 | 3/3 | 3/3 |
| 已点名的共享词 | 2026年8月的有效支付金额（也就是销售额）是多少？ | 3/3 | 3/3 |
| 共享词，应澄清 | 2026年8月销售额是多少？ | 0/3（静默生成查询） | 3/3（服务端澄清，0 次模型调用） |
| 范围外，应澄清 | 2026年8月的退款金额是多少？ | 3/3 | 3/3 |
| **合计** | | **12/24** | **24/24** |

回归：原 4 道黄金题（无前缀）4/4 计划由唯一覆盖模型解析、执行并对账通过，含糊问题仍澄清。

## 发现

- **修订连锁**：发布引用固定到具体修订，规划器要求模型引用当前修订。给被引用的知识加词汇，需要按依赖顺序重新固定派生知识和模型，一次词汇变更变成了三次治理操作。这对作者是明显摩擦，建议把只改词汇、不影响计算的修订视为兼容，或在编辑器中提供一键重新固定。
- **审计**：服务端澄清原先也会记录一条 `model` 步骤，已改为 `tool:ask_disambiguation`，审计不再声称调用过模型。
- 去掉前缀后不需要指定模型，原因是提示词不再强制要求，规划器本来就会选择唯一覆盖的模型。
