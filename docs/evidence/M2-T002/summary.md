## Delivered

- Migration `000006_m2_governed_authoring` (+ down): all ten tables from `data-model.md` — `proposals`, `proposal_changes`, `reviews`, `validation_runs`, `validation_results`, `policy_decisions`, `releases`, `release_assets`, `agent_runs`, `agent_steps` — every one carrying workspace scoping (`workspaces` FK on aggregate roots; composite `(workspace_id, root_id)` FKs for children, mirroring the M1 `source_revisions` pattern), UUIDv7 identity checks, and M1-style CHECK/trigger discipline. The downgrade drops only M2 tables plus the two new functions; M0/M1/T001 schema and rows are untouched (proven by the populated-upgrade suites).
- Domain layer `internal/domain/governance`: the SSOT §7.5 proposal state machine as an explicit transition table (`draft → proposed | rejected`, `proposed → validating | rejected`, `validating → in_review | rejected`, `in_review → released | rejected`; `released`/`rejected` terminal, no-op transitions legal), enforced with `ErrInvalidTransition`/`*TransitionError` before any database write; `ChangeSetItem` with `field_path`/`op`/`before_digest`/`after_digest`/`before_value`/`after_value` and op-shape validation plus `ChangeSetEditable` (frozen once the proposal leaves draft); closed `ProposalState` vocabulary that deliberately excludes lifecycle/deployment/health states (§4.8); `Review` (§8.4 channels), `ValidationRun`/`ValidationResult` with the §3.3 severity enum (`blocker` blocks release candidacy), recomputable `DecisionInputs` + `EvaluateRiskRule` (pure, versioned `1.0`), `Release`/`ManifestEntry` with canonical `ManifestDigestPayload`, and `AgentRun`/`AgentStep` per §8.6 (hashes only).
- Canonical-JSON recomputability: `CanonicalJSON`/`DigestJSON` (precise-number decode, recursively sorted object keys, no insignificant whitespace, number literals preserved verbatim, 1 MiB bound) produce the `sha256:` `inputs_digest`; the same helpers make `manifest_digest` recomputable.
- Application layer `internal/application/governance`: persistence-oriented `ProposalService` (draft authoring with change-set add/remove, `Submit` = draft→proposed with change-set freeze, `Transition`, rejection with `decided_at`, `RecordReview`), `ValidationService` (start run, record result, finish with Blocker gate, `HasBlockers`), `PolicyService` (`Decide` = strict parse → canonicalize → versioned rule → immutable row + proposal link, `GetDecision`), `ReleaseService` (`Cut` with in_review/Blocker gating, `Rollback` = new release row referencing the target and restoring the preceding release's manifest), `AgentRunService` (`Start`/`RecordStep`/`Finish` with terminal final state). All event identities (audit + outbox pairs) are pre-minted in the services exactly like M1's `newRevisionEventIDs()`.
- Transaction discipline: proposal submission, state transitions, policy decisions, release cuts and rollbacks each run inside one transaction following the M1 `AppendCatalogRevision` pattern — parent row `FOR UPDATE` lock (proposal) or workspace lock (releases) → sequence allocation → inserts → audit fact + outbox event → single commit. New outbox envelopes `proposal.changed` (`semlia.proposal/v1`) and `release.published` (`semlia.release/v1`) use the strict `semlia.events/v1` envelope (strictly decoded in tests with `DisallowUnknownFields`), and audit facts use `governance.proposal.*` / `governance.release.*` event types.
- Refactor per packet: `internal/adapters/postgres/mutation_events.go` extracts the shared audit+outbox plumbing (`createMutationEvents`) from the M1 catalog pattern; `createCatalogMutationEvents` now delegates to it (serialized bytes unchanged — the strict M1 projection publisher and journey suites pass untouched), and both `proposal.changed` and `release.published` emissions reuse the same function.
- Immutability as repository invariant + defense in depth: `proposal_changes` are freely editable only while the parent proposal is `draft` (trigger `guard_proposal_change_set` rejects insert/update/delete otherwise, ERRCODE 55000); `reviews`, `validation_results`, `policy_decisions`, `releases`, `release_assets`, `agent_steps` are fully immutable via `reject_immutable_registry_row()` triggers; `proposals` carries a `validate_proposal_state_transition` trigger that mirrors the domain table and freezes terminal rows. No repository method exposes update/delete for any immutable table.
- Dispatcher policy (unregistered outbox types): the router stays fail-closed (`ErrPublisherNotRegistered`), and `Dispatcher.RunOne` now treats that sentinel as a completion signal — the event is marked `published` in exactly one attempt instead of burning `max_attempts` retries toward a dead letter. Nothing is registered in production wiring for `proposal.changed`/`release.published` (T003 wires the first consumers); the policy is documented in code and proven by unit tests (one clean attempt for unregistered types; generic publisher failures still retry and dead-letter).
- `pkg/identity`: new TypeID prefixes registered per ADR-0003 — `prp_` (proposal), `chg_` (proposal change), `rvw_` (review), `val_` (validation run), `vlr_` (validation result), `pol_` (policy decision), `agr_` (agent run), `ags_` (agent step); `rls_` already existed for releases (M1) and gained the missing `ReleaseIDFromUUIDBytes`. `prn_`/`bnd_` remain T001's.
- sqlc: `db/queries/governance.sql` (26 queries incl. `GetProposalForUpdate`, `LockWorkspace`, `NextReleaseSequence`, `CountBlockingValidationResults`) + generated `internal/adapters/postgres/sqlc/governance.sql.go`; `db/sqlc.yaml` includes migration 000006; repository adapter `internal/adapters/postgres/governance.go` implements the five service repository interfaces in the M1 store style.
- No HTTP endpoints, no OpenAPI or sdk/typescript changes (`make contracts-check` green); no workflow/lifecycle/deployment/health enum collapse; no raw prompts or credentials — the agent-run schema has no field that could hold them (hash/digest CHECKs only).

## Review Boundary

Deviations and decisions for reviewer attention:

1. **Exact proposal transition table implemented**: `draft → proposed | rejected`, `proposed → validating | rejected`, `validating → in_review | rejected`, `in_review → released | rejected`; `released`/`rejected` terminal; no-op transitions legal. Beyond the two rejection edges named in the task (`draft→rejected`, `in_review→rejected`), `proposed→rejected` and `validating→rejected` are included because SSOT §8.2 ends the pipeline in "immutable release **or rejection**" at any stage and the §7.5 diagram hangs `rejected` off the pre-release path. The application additionally refuses `Transition(→released)` (release cut is the only path); the domain table itself keeps the §7.5 edge legal.
2. **Dispatcher policy for unregistered outbox types**: `ErrPublisherNotRegistered` completes the event as `published` in one attempt. Rationale: an event with zero registered subscribers needs no delivery, and the alternative (retry-to-dead-letter) would poison the dispatch loop with 8 wasted cycles per governance mutation until T003. The router remains fail-closed; production wiring registers nothing for the two new types; payload remains queryable in `outbox_events` per M0 retention, and the audit fact is permanent. Proven by `TestUnregisteredEventTypeCompletesWithoutRetry`; generic publisher failures still retry/dead-letter (`TestPublisherFailureStillRetries`).
3. **Digest canonicalization**: canonical JSON = decoded with `json.Number`, re-encoded with recursively sorted object keys and no whitespace; number literals preserved verbatim (`1.500` ≠ `1.5`) and array order significant. `policy_decisions.inputs` are stored in canonical form and validated against the closed `DecisionInputs` schema (unknown fields rejected), so digest equality is total over the stored feature set; `UNIQUE (proposal_id, rule_version, inputs_digest)` makes one decision per inputs+version a storage invariant. Risk rule `1.0` is a pure function with stable reason codes (`RISK_BLOCKER`, `RISK_PRODUCTION_COMPUTATION`, `RISK_ACCESS_OR_CONTRACT_CHANGE`, `RISK_COMPUTATION_CHANGE`, `RISK_PRODUCTION_CHANGE`, `RISK_LOW_BATCH`); the routing vocabulary is `expert|batch` per data-model.md.
4. **`releases.sequence` added beyond the data-model key shape**: the M1 discipline (row lock → monotonic sequence → keyset ordering) requires a stable per-workspace release order; `NextReleaseSequence` runs under the workspace lock, mirroring `AppendCatalogRevision`.
5. **Rollback semantics for T002**: a rollback publishes a NEW release row whose `rolled_back_to_release_id` references the target and whose manifest copies the entries of the release preceding the target by sequence (empty manifest when the target is the first release — a withdrawal); each release can be rolled back at most once. Rows are never mutated, so `releases.state` inserts only `published` (`rolled_back` stays in the CHECK vocabulary for T007 surfacing). Richer rollback policy (canary, rebind) is T007 scope.
6. **Blocker severity semantics**: `FinishRun(succeeded)` is refused while the run's own findings contain a Blocker; the release cut blocks on Blocker findings belonging to `running|succeeded` runs — findings from `failed|cancelled` runs are unusable (the harness failure invalidates them, §8.2 "degrade to human handling"), keeping the gate precise without a new status value.
7. **`target_object_*` generalization**: `proposals` accepts the four §11.2 object types with a shape CHECK; T002's application only creates `semantic_asset` proposals (FK to `semantic_assets`/`asset_revisions`); 000007 adds the remaining object tables and per-type FKs.
8. **Agent-run recording**: cost is stored as `cost_micros bigint` (avoids numeric/float ambiguity), duration as `duration_ms` computed from the injected clock at finish; the request structs carry hashes only — no prompt/credential field exists to leak.
9. **Existing test-expectation updates**: `tests/integration/db/database_test.go` now expects migration version 6, ten additional tables in the inventory, the workspace-FK list extended by the four new aggregate roots (`proposals`, `releases`, `reviews`, `agent_runs` — children scope via composite FKs per the M1 convention), `Steps(5)` with one extra downgrade step in the populated-M0 suite, and a new populated-M1 suite. No assertions were weakened.
10. **No production wiring changes beyond the dispatcher policy**: `cmd/semlia` still registers only the catalog projection publisher; governance services are not yet attached to HTTP (T003). `internal/application/governance` services take plain repository interfaces so T003 can compose authorization evaluation on top unchanged.

Residual work belongs to T003+: HTTP contracts over these services, publisher registrations for `proposal.changed`/`release.published` (the dispatcher now completes unregistered types safely either way), and T007's release orchestration on top of the immutable rollback rows.
