## Delivered

- Governance API client (`web/src/governance.ts`, new): mirrors `catalog.ts` discipline — typed async functions over the generated SDK client (`createSemliaClient`), zero ad-hoc fetch. Covers every endpoint in the packet: proposals (list/create/get/submit), validation runs, policy decisions, reviews, review batches (list/assemble/get/confirm), releases (list/publish/get/rollback), model providers/settings (list/create/update/set-default) and generation (`agent-runs/generate-proposal`). A `GovernanceApiError` carries the stable wire `code` (`SEPARATION_OF_DUTY`, `NOT_FOUND`, `CONFLICT`, `PROVIDER_UNAVAILABLE`, `PROVIDER_UNSUPPORTED`, `AI_OUTPUT_INVALID`, `NO_SUBSTANTIVE_CHANGE`, `BLOCKED_BY_FINDINGS`, `NO_APPROVING_REVIEW`, `PROPOSAL_NOT_IN_REVIEW`, …) plus the API `details`, verified against the backend's `writeGovernanceError` mapping. `getPolicyDecision` maps the "no decision before validation completes" 404 to `null` instead of an error.
- Governance runtime (`web/src/governanceRuntime.tsx`, new): one provider (`GovernanceRuntimeProvider`) shared by every M2 view. Holds the proposals/releases/batches/model-providers lists with `idle|ready|error` states (list failures are surfaced as error banners, never fixture data), caches validation runs and policy decisions per proposal, keeps the session cache of recorded reviews (the API exposes no review-list endpoint), derives `workflowStateByAsset` from real proposal states, exposes all actions (create+submit, review, batch assemble/confirm, publish, rollback, model-config CRUD, generation), and resolves release manifest pins to human revision labels (`@N`) via the M1 `listAssetRevisions` endpoint with caching. Release details are fetched alongside the list so manifest pins can render without N+1 clicks. A `fixture` prop (reachable only from `VITE_CATALOG_FIXTURE=1`, see below) swaps the real client for the fixture client behind an identical `GovernanceApi` interface.
- Fixture harness (`web/src/governanceFixture.ts`, new): an in-memory stateful implementation of the same `GovernanceApi` shapes seeded from the accepted session experience (`data.ts` proposals/releases/model lists), reachable only when `App.tsx` passes the `VITE_CATALOG_FIXTURE=1` flag down — the exact existing e2e pattern. It simulates the full loop deterministically: draft → submit (runs + decision generated, `in_review`) → expert/batch review → publish (release #N with manifest pinning `assetId@revision`) → rollback (new release referencing the target). `scripts`/backend untouched; the harness stores only digest-shaped credential revisions, mirroring the real non-echo shape.
- Authoring flow (`web/src/KnowledgeRevisionWorkbench.tsx`, `web/src/ProductApp.tsx`): 提交审核 now creates a REAL proposal — `POST governance/proposals` with `targetObjectType: semantic_asset`, the asset TypeID, the current revision as `baseRevisionId` (rev_ TypeIDs only), `createdBy: "catalog-web"` (M1 createAsset discipline) and a structured change-set derived from the field edits (multiline fields become arrays; `op` inferred add/update/remove) — then `POST …/submit`. The pre-submit 运行检查 keeps its guard role (changed fields + mandatory reason) with honest copy ("提交后由治理验证器执行"); the fake "3/3 完成" claim is gone. Submission failures render in the workbench error area. After submit the UI navigates to the candidate detail, which fetches and POLLS `validation-runs` (1.6 s while any run is `running` or the proposal is `validating`) and renders per-run validator id + version (`schema|reference|structural v…`), run status, per-result severity badges (blocker/warning/info/not_applicable) and result messages.
- Policy decisions: the candidate detail fetches the latest `GovernancePolicyDecision` and renders risk level (低/中/高风险), routing channel (专家评审/批量确认), matched rule id, reason code, rule version and the explainable reason text. Asset detail's 可信度 tab gains a 治理流水线 section (提案验证与策略决策) listing every non-draft proposal for the asset with its runs and decision when present.
- Review surface (变更与发布, `ReleasesView` in `web/src/ProductApp.tsx`): lists real proposals (proposed/validating/in_review/rejected rows with state badges, per-proposal policy badges fetched on mount, asset name/key resolved from the catalog runtime) and real releases sorted by sequence (当前版本 = latest sequence; rollback releases marked 回滚发布). ReviewDialog records real reviews — approve/reject with MANDATORY reason (both buttons disabled until text is entered) — and renders 403 `SEPARATION_OF_DUTY` failures as a dedicated conflict block carrying the wire code, the API's `conflict` explanation and its `policySource`; other failures render with their stable code. The fake 发布身份 select is gone; the dialog explains that separation of duty is enforced server-side (FR-007 / D-006).
- Batches: a 评审批次 surface on the releases view lists open batches (GET), assembles new ones (POST, empty result → visible "没有符合条件" toast), expands to the full audit record (grouping rule, policy version, members with sample badges, max-risk member, confirm-time exclusions with reasons) and confirms with a decision + mandatory reason via a dedicated dialog that renders SoD conflicts the same way. Batch actions are capability-gated (`proposal.review`).
- Publish + rollback: PublishDialog shows the real gates (blocker findings from validation runs, approving-review presence, consumer-impact summary) and cuts the release via `POST governance/releases {proposalId}`; success renders the immutable record (release id, sequence, manifest digest, origin proposal) on the candidate and the row list. ReleaseDetail renders the immutable record — manifest strip (sequence/state/digest/publisher/time), manifest pins (asset revision pins and governed-object version pins with resolved `@N` labels), origin proposal change-set when resolvable, the `rolledBackToReleaseId` reference on rollback releases and a computed "已被 … 回滚" reference on rolled-back targets — and rollback issues `POST …/rollback`, rendering the NEW release with its restored prior-revision pin. Release-consumer bindings remain as an explicitly labeled 原型数据 block (M3 surface) so nothing claims persistence for session-only data.
- Model configuration (`web/src/ModelConfigurationView.tsx`): reads real `GET model-providers` (loading/empty/error states — error banners, never fixture fallback). Protocol select maps openai/anthropic/gemini/openai_compatible; provider identity shows the credential env-var name and the revision digest as the "Key v{digest}" marker. Provider enable/disable and credential rotation go through `PUT model-providers/{id}` (rotation dialog takes the write-only credential + optional env name); model create/edit/toggle go through `POST/PUT model-settings`; set-default calls the dedicated `POST …/set-default` endpoint (409 CONFLICT from disabled models surfaces as a visible failure). The add-provider dialog requires 配置名称, protocol, `credentialEnv` (uppercase env-NAME), the write-only password `credential`, and `baseUrl` for openai_compatible — submit disabled until filled; the secret is `type="password"`, never stored in rendered state after submit, and responses contain no credential field. The embedding rebuild flow keeps its 原型 labeling (T009 boundary) and the footnote now states real persistence for configuration.
- AI generation (`web/src/AIProposalDialog.tsx`, new; entry in the workbench header "AI 提案"): requires a configured default LLM — without one it renders a helpful empty state with a 打开模型配置 action that navigates to the model settings. With one configured it calls `generate-proposal` and renders the created agent-attributed draft: agent-run facts (run id, model, config revision, cost/duration) plus the proposal's change-set as a diff, then 提交 AI 提案 walks it through `POST …/submit` into the normal review pipeline. Provider failures render as visible failure blocks with the stable code and the API message (`PROVIDER_UNAVAILABLE` 503, `PROVIDER_UNSUPPORTED` 422, `AI_OUTPUT_INVALID` 422) — no silent retry, no fallback.
- Runtime seam (`web/src/catalogRuntime.tsx`, `web/src/App.tsx`): `CatalogRuntimeProvider` accepts a `setWorkflowStateOverlay` and projects `revisionRecord.workflowState` per asset from the overlay (`released` remains the default); `ProductApp` feeds it `workflowStateByAsset` derived from real proposals (draft→draft, proposed/validating→proposed, in_review→in_review). The projection is a render-derived memo so it applies to both the fixture path and the real fetch path. The fixture path stays exclusively behind `VITE_CATALOG_FIXTURE=1`; production API failures render error states everywhere (locked by test).
- Command palette and 创建变更事项 now operate on real data: the palette lists runtime proposals (state-labelled) and opens their candidate detail; 创建变更事项 routes into the real revision workbench for the selected asset instead of fabricating a session draft. The releases context-panel meta (候选/已发布 counts) is computed from runtime state.
- Preview discipline: Ask, 数据接入 (JourneyViews), integration administration, access control, audit/runtime and catalog controls are untouched (`git diff` empty for those files) — all preview/session labels preserved. Fully-real governance surfaces dropped their preview copy ("原型决策仅保留在当前会话" etc.); the partially-real release detail labels its consumer-binding block as 原型数据.
- New e2e governed journey (`web/e2e/product-journey.spec.ts`): author (asset detail → 修订知识 → field edit + reason) → submit (real proposal navigation) → validation visible (3/3 runs, validator id/version, policy decision with matched rule/routing) → review decision (mandatory reason → approve) → publish (release record with sequence #7) → rollback (new release #8, target referenced, registry pointer restored, asset detail governance evidence) — running under the fixture flag on both desktop projects (1440x900, 1024x768) with overflow checks. Existing journeys were converged to the real flows (row labels, review/publish dialogs, model-config ids) without losing a single assertion's intent; the access-control journey now proves the mandatory-reason gate and the server-side separation-of-duty disclosure instead of the removed fake publisher selector.

## Review Boundary

Deviations and decisions for reviewer attention:

1. **UI-authored proposals set `createdBy: "catalog-web"`**: the backend compares the proposal's `CreatedBy` string against the reviewer principal for FR-007 separation of duty. The web has no principal identity surface in incubation (empty `X-Semlia-Principal` = seeded workspace admin), so attributing UI-authored proposals to the admin's TypeID would make the founder's own author→review→publish journey impossible in the browser. `catalog-web` follows the M1 `createAsset` discipline, keeps the governed loop operable end to end (packet acceptance), and the SoD machinery remains fully server-enforced — locked by the conflict-rendering test that feeds the real wire shape (`SEPARATION_OF_DUTY` + `conflict` + `policySource`). A future identity surface can pass the real principal here without further changes.
2. **`VITE_CATALOG_FIXTURE=1` also switches governance to the in-memory fixture harness**: the packet asks to "extend the fixture server/harness for governance endpoints following the existing VITE_CATALOG_FIXTURE pattern". The existing pattern is an in-app fixture injection (`fixtureAssets`), not a separate server, so governance follows it with a `fixture` provider prop that only `App.tsx` sets under the flag. Production failures cannot reach the fixture path (separate module, single flag-gapped seam) and the never-fallback requirement is locked by a component test that runs the real client against rejecting mocks.
3. **Seeded fixture proposals keep their accepted identifiers** (`PROP-128`, `PROP-126`, `PROP-121`, `release-2026.08.3`…): the fixture path exists to preserve the accepted product experience for browser journeys, and the existing e2e asserts those identifiers. The real client is fully TypeID-typed; the fixture strings never pass through `governance.ts`. Duplicate seeded release ids were made unique (React key integrity) by suffixing the sequence.
4. **Reviews are cached per session from their API responses**: the contracts expose no "list reviews of a proposal" endpoint, so after a reload the UI cannot re-derive approval state; the server still enforces every publish gate (publishing without an approval returns `NO_APPROVING_REVIEW`, rendered verbatim). If a review-list endpoint lands later, the runtime cache is the only thing to replace.
5. **Fixture harness simulates validation synchronously**: submit immediately produces terminal runs + decision + `in_review` so e2e is deterministic. The polling client path is still exercised (the candidate detail polls while runs are `running`/state is `validating`); real deployments with a separate `semlia worker` see the empty-runs "等待执行" state until the worker lands.
6. **Consumer bindings on release detail are labeled 原型数据**: the release contracts carry no consumer information (M3), but the accepted experience shows them. The block now renders the session preview data under an explicit "消费绑定 · 原型数据 / 真实消费绑定属于 M3 交付里程碑" label rather than silently claiming persistence.
7. **"当前版本" is derived as the highest release sequence**: rollback cuts a new release (the wire's only truth), so the latest row — rollback or cut — is the served version, and a rolled-back target shows a computed "已被 … 回滚" reference derived from the new release's `rolledBackToReleaseId` (the target row itself is never mutated by the backend).
8. **Candidate revision labels (`@N`) are resolved, not invented**: manifest pins carry `rev_` TypeIDs; the runtime resolves them to sequences via the M1 revisions endpoint (cached, failure-tolerant to the raw TypeID), and fixture pins embed `@N` directly. Fixture-created candidates display `@{current+1}` derived from the catalog's current revision sequence, mirroring the accepted 候选版本 presentation.
9. **The fake publisher-identity selector in PublishDialog was removed** rather than adapted: publishing is executed by the authenticated principal and the two-person rule is server-enforced, so a client-side identity switcher would be a false control. The e2e access-control journey now proves the mandatory reason gate plus the server-side SoD disclosure; the conflict-alert rendering itself is locked by the `SEPARATION_OF_DUTY` component test.
10. **创建变更事项 now routes into the revision workbench** instead of creating a session-only draft: the dialog has no change-set input, and fabricating session proposals on a governance surface would violate the preview discipline; routing to the real authoring path keeps the accepted entry point and makes the result a real, persisted proposal.
11. **`internal/platform/web/static` embed assets changed**: they are the generated output of the required `make check-source` web-embed-drift gate (the embedded production build of the allowed `web/**` tree), not hand edits; no other `internal/**`, `api/**` or `migrations/**` files were touched.
12. **`docs/specs/m2-governed-authoring/packets/T010.yaml` remains untracked** (input packet, not a deliverable); no spec files were modified.
