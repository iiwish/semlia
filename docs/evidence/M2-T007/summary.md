## Delivered

- Migration `000010_m2_release_publishing` (+`.down.sql`): `releases.origin_proposal_id uuid` (nullable, workspace-scoped FK to proposals) linking each cut to the proposal it released, and `release_objects` (PK `(release_id, object_type, object_id)`, workspace FK to releases, `object_type` closed CHECK, `version > 0`, `position` with `UNIQUE (release_id, position)`) pinning governed-object versions exactly the way `release_assets` pins asset revisions. The existing `releases`/`release_assets` immutability triggers are untouched; `release_objects` gets the same `reject_immutable_registry_row` trigger. `database_test.go` expectations moved to version 10 (inventory, migration step counts, per-step rollback labels) without weakening any assertion; the tenant-FK list is unchanged because both new FKs are workspace-scoped composites.
- Publish command `POST /api/v1/workspaces/{workspaceId}/governance/releases` body `{proposalId}` → 201 release detail. Gate order (all server-side, per packet): (1) proposal exists and is `in_review` → 409 `PROPOSAL_NOT_IN_REVIEW`; (2) no reliable Blocker findings (T002 `CountBlockingResults`) → 422 `BLOCKED_BY_FINDINGS`; (3) ≥1 approving review exists (T006 immutable `reviews` rows, decision `approved`, any channel) → 422 `NO_APPROVING_REVIEW`; (4) publisher holds `release.publish` through the T001 evaluator (workspace-scope resource; the `requires_human` flag auto-refuses agent principals with 403 `SEPARATION_OF_DUTY`); (5) publisher ≠ proposal `created_by` → 403 `SEPARATION_OF_DUTY` (`PUBLISHER_IS_AUTHOR`); (6) publisher ≠ the sole approving reviewer when exactly one approving review exists → 403 `SEPARATION_OF_DUTY` (`PUBLISHER_IS_SOLE_REVIEWER`). Every refusal writes an immutable `governance.release.denied` audit fact (`reasonCode`, `policySource`, `proposalId`/`releaseId`, `conflict` for SoD) on top of the `authorization_events` rows the evaluator already commits for capability denials.
- Publish application in ONE transaction (per target, inside `PublishRelease` in the store): `LockWorkspace` → `GetProposalForUpdate` with an in-state re-check (defense in depth) → change-set application → release cut. Semantic-asset target: asset row locked `FOR UPDATE`, the proposal base revision must still be the asset's current revision (optimistic concurrency; else stable conflict), the change-set is applied to the current content by the shared domain helper (`ApplyChangeSet`: add requires absence, update requires presence, remove deletes; dotted field paths; canonical re-encode), a new revision is inserted with the next sequence and the sha256 content digest, `SetCurrentAssetRevision` switches the pointer, and the exact M1 envelope pair (`catalog.asset.changed` / `governance.asset_revision.created`, action `revision.created` with `baseRevisionId`) is emitted so the Git asset content follows the publish. Governed-object target: the object row is locked through the T008 spec pipeline, the expected version is read under the lock, the change-set is applied to the object content, exactly one version bump is applied, and the T008 audit-only fact (`governance.<type>.applied`, version, actor) is recorded. Then the release cut: next workspace sequence, manifest = one entry pinning the resulting asset revision (compatibility `{}`) or governed-object version, `manifest_digest` = sha256 of the canonical manifest payload (`ManifestDigestPayloadWithObjects` — asset-only manifests keep the byte-identical T002 payload shape; object pins add an `objects` array), `releases` row (state `published`, `origin_proposal_id`) + `release_assets`/`release_objects` pins, proposal walked `in_review → released` with `decided_at`, and audit + outbox (`governance.release.published` fact; `proposal.changed` action `released`; `release.published` envelope `semlia.release/v1`) all committed atomically. Rollback of the transaction removes every trace (atomicity asserted by the gates writing nothing on refusal).
- Git release projection: a `ReleasePublisher` is registered in the projection router for `release.published` (worker wiring in `cmd/semlia/main.go`). It strictly decodes the `semlia.events/v1` envelope and the `semlia.release/v1` data contract (DisallowUnknownFields both levels; `action` must be `published|rolled_back`; `rolledBackToReleaseId` presence must match `rolled_back`), loads the release read model (`LoadReleaseProjection`: release row + asset pins with readable addresses + object pins as TypeIDs + originating proposal metadata) and hands it to the EXISTING gitcontent writer: new method `ProjectRelease` appends `semlia.io/v1 SemanticAssetRelease` documents at `releases/<sequence>-<releaseId>.json` (manifest assets with `assetId/revisionId/address/compatibility/position`, manifest objects with TypeID `objectId/version/position`, proposal metadata, release metadata incl. `rolledBackToReleaseId`), committed with message `project release <releaseId> <sequence>` on top of the current head. Same discipline as assets: dirty-worktree guard, atomic file write, idempotent re-delivery (existing release file → no-op commit), and NO tags, NO remotes, NO reverts, NO history rewriting — locked by the append-only graph test (every commit exactly one parent, root has none, only the default branch ref exists, zero tags, zero remotes, commit count == projected events). Asset content projection via the existing `catalog.asset.changed` path is verified unchanged in both directions (publish and rollback switch the projected revision document).
- Rollback command `POST /api/v1/workspaces/{workspaceId}/governance/releases/{releaseId}/rollback` (no request body; non-empty → 400) → 201 the new release detail. Gates: human-only `release.rollback` capability (agents refused `SEPARATION_OF_DUTY` by the evaluator), target exists and is `published` (409 otherwise), one-rollback-per-target (T002 `CountReleaseRollbacks`, 409 `RELEASE_ALREADY_ROLLED_BACK`, re-checked inside the transaction under the workspace lock), target is the latest release (409 `RELEASE_NOT_LATEST`, so the restore is well-defined), and — when the target originated from a proposal — the rollback publisher ≠ that proposal's author (403 `SEPARATION_OF_DUTY`). The rollback creates a NEW immutable release (D-008) referencing the target via `rolled_back_to_release_id` and restores application state in the SAME transaction: asset targets switch the current-revision pointer back to the prior pinned revision (the newest `release_assets` pin with sequence < target, falling back to the originating proposal's base revision; refusal `PRIOR_STATE_UNKNOWN` when neither exists) and emit `catalog.asset.changed` so Git content follows the pointer; governed-object targets apply the inverse change-set (`ApplyInverseChangeSet`: update restores `before_value`, add removes the field, remove re-writes the removed `before_value`) as a new version bump with its T008 audit fact, and the rollback manifest pins the resulting restored version. Untouched entries are carried over from the release preceding the target (T002 semantics); the target release rows are never mutated (verified: state stays `published`, digest unchanged, second rollback refused).
- Release read surface: `GET .../governance/releases` (keyset `published_at DESC, id DESC` with the T003-style opaque cursor) and `GET .../governance/releases/{releaseId}` (detail with manifest assets + objects, `rolledBackToReleaseId`, `originProposalId`, digest). All reads evaluate `asset.read` at workspace scope (documented choice: release manifests pin assets; the vocabulary has no release-level read action that is not human-gated). TypeIDs only on the wire (`rls_` release id, `ast_/rev_` pins, object TypeIDs) — no storage UUIDs (locked by test).

## Review Boundary

Deviations and decisions for reviewer attention:

1. **New `PublishingService` rather than extending T002 `ReleaseService`** (packet allowed either): T002's `Cut`/`Rollback` keep their exact contracts and tests; the governed loop (capability + approval + two-person gates, change-set application, state restore) composes over the same store as `PublishingService`, auto-wired inside `NewAuthoringService` when the repository implements `PublishingRepository` (same discovery pattern T006 used for `ReviewBatchRepository`). T002's `CutRelease` additionally records `origin_proposal_id` when a proposal is resolved, so T002 cuts gain the link without behavior change.
2. **`release_objects` table + digest extension**: the T002 manifest schema (`release_assets`) can only pin asset revisions, so governed-object pins need the new table and the digest payload gains an `objects` array when objects are pinned. Asset-only manifests keep the byte-identical T002 canonical payload (locked by unit test), so digests of asset-only releases are unchanged.
3. **Rollback manifest rule (packet tension resolved)**: the packet asks for "manifest = the release preceding the target" AND "object targets restore content as a new version bump". A literal previous-manifest copy would pin an object at its pre-publish version while the restored content carries a new version — an untruthful manifest. The implemented rule: entries for targets the rollback actually restores are pinned at the restored state (asset pointer revision / object restored version); untouched entries are carried over from the preceding release; positions renumber deterministically. For the single-target v1 publish path the rollback manifest is exactly the restored pin.
4. **Rollback is restricted to the latest release** (`RELEASE_NOT_LATEST`): restoring prior state under a newer release would silently contradict that newer release's manifest (it stays immutable). T002's non-restoring `Rollback` keeps its original semantics for the substrate-level tests; only the T007 state-restoring command adds the guard.
5. **Rollback SoD**: the capability gate is `release.rollback` (human-only, agents auto-refused). The publisher≠author two-person rule applies when the target release originated from a proposal (the author of the change being undone must not undo it alone); there is no approval fact for rollbacks, so the sole-reviewer rule has no rollback analogue — documented v1 reading of "same capability + SoD gates".
6. **Publish gate order follows the packet list literally** (state → blockers → approvals → capability → author → sole reviewer), so e.g. an agent principal publishing an unapproved proposal is refused with `NO_APPROVING_REVIEW` (422) rather than a capability code — the tests pin this order. Capability denials are audited twice by design: the T001 `authorization_events` row (allow+deny, FR-013) plus the `governance.release.denied` refusal fact.
7. **Asset publish requires the proposal base to still be current** (`ErrConflict`): the change-set digests are advisory (the T003 wire accepts opaque digests and tests use synthetic ones), so digest re-verification is not enforceable; the pointer check is the enforceable optimistic-concurrency gate for assets. Governed-object publishes read the expected version under the row lock instead (object proposals record no base version), which is last-writer-wins within the publish transaction — a documented v1 limit inherited from the T008 patch shape.
8. **Rollback emits `catalog.asset.changed` for restored assets** (action `revision.created`, `baseRevisionId` = the replaced revision): the packet's projection requirement ("make it so the projected asset content updates") is satisfied for both publish and rollback; the envelope shape is exactly the M1 one, so the existing publisher consumes it unchanged.
9. **`manifest_digest` is recomputed inside the transaction from the pinned entries** (shared `ManifestDigestPayloadWithObjects`), so a release row and its pins can never disagree; the HTTP test recomputes the digest from the wire manifest and matches it against the release detail.
10. **`ProposalService.Transition` already refuses the `released` edge** — the release path transitions the proposal inside the publish transaction (`ExpectedState: in_review`), exactly like T002's cut; no new transition route exists.
11. **`POST .../rollback` takes no body** (deterministic command; non-empty → 400, mirroring T006 batch assembly). Recovery/justification belongs to the audit layer (`governance.release.rolled_back` fact records actor and target).
12. **`docs/specs/m2-governed-authoring/packets/T007.yaml` is untracked** in the working tree (input packet, not a deliverable); no spec files were modified.

Residual work belongs to M3 (consumer bindings and trusted resolution read the release manifest; deployment/environment surfaces) — the release rows, manifests, Git documents and rollback mechanics delivered here are the substrate those features bind to.
