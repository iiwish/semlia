Gate order: (1) `asset.propose` evaluated server-side for the CALLING principal on the proposal target resource (403 on denial, before any run exists); (2) deterministic target snapshot loaded — semantic assets pin address + current revision id/content (no revision → stable failure), governed objects pin version + content through the T008 read path; (3) model resolution — explicit `modelSettingId` (must be an enabled llm of the workspace) or the enabled default llm (query joins enabled settings of enabled providers; none → 409); (4) protocol check — non-generating protocols answer 422 `PROVIDER_UNSUPPORTED` before any run opens (nothing to record: no provider execution was attempted); (5) run lifecycle (T002 service) with `PrincipalID` = the workspace's seeded agent principal (D6), `Model` = setting model, `ConfigRevision` = `<credential_revision>/<model_setting_id>` (so a credential rotation or model edit changes the attribution), `InputHash` = sha256 of the canonical JSON generation input `{schema, targetObjectType, targetObjectId, baseRevisionId?, target snapshot, instruction, outputSchema}` — the embedded semlia.proposal-input/v1 schema bytes are part of the hashed input; (6) one `Complete` call whose user prompt is rendered deterministically from the same canonical input plus fixed header lines and the exact `agentAttribution` echo the output must carry (`agentRunId/model/configRevision` from the run, `inputHash` as hashed) — attribution is server-derived metadata injected into the prompt only, never into the hashed payload (no circularity); (7) §8.6 step recording: sequence-1 `model` step with the input hash, output hash (digest of raw content, or of the error detail on failure) and stable `error_code` (`PROVIDER_UNAVAILABLE`/`PROVIDER_UNSUPPORTED`/`AI_OUTPUT_INVALID`/none); (8) the T003 schema gate — the output's outermost JSON object (markdown fences tolerated) is parsed, its attribution echo is verified against the run (mismatch → `AI_OUTPUT_INVALID`), change-set digests are RECOMPUTED from the provided before/after values (model-emitted digests are never trusted), the document is re-encoded with the server-owned attribution and validated through the embedded versioned schema — on violation the run finishes `failed` and the API answers 422 `AI_OUTPUT_INVALID` with bounded violations, no proposal; (9) on gate pass the proposal is created through the EXISTING T003 authoring path (`CreateProposal` with the matching `AgentAttribution`), which re-authorizes the caller and attributes authorship to the agent principal — the generated proposal enters the normal validating/review pipeline (submission walks it to `validating`, locked by test); a sequence-2 `tool` step (`create_proposal`) records the domain write with the payload input hash and the created-proposal output hash; (10) `Finish` records the final state, output digest (canonical gated payload), cost and duration. **Cost mapping:** `cost_micros` = prompt + completion tokens (one micro per token — a normalized-usage placeholder until pricing adapters land with the remaining protocols). **Idempotency:** one request = one run = at most one proposal; there are no implicit retries — a retry is a new explicit request with a new run, so proposals cannot be duplicated silently. Every failure path after run start finishes the run `failed` (duration, terminal state, no output digest) — the degradation contract.

## Review Boundary

Deviations and decisions for reviewer attention:

1. **Credential handling follows the task's "simplest safe design" literally**: the API accepts a write-only `credential` (secret material) alongside the required `credentialEnv` NAME; the server immediately reduces it to a domain-separated digest (`sha256("semlia.credential.v1:" + secret)`) and discards it. Nothing secret is persisted, logged or echoed (locked by column-walking and response-scanning tests). A stricter alternative — rejecting any credential field and accepting only the env name — was rejected because the packet explicitly requires the DB to store "a sha256 digest of the provided secret for revision tracking", which is only defined when a secret is provided.
2. **`credentialRevision` is a digest, not the view's counter**: the ModelConfigurationView renders "Key v3" (a monotonic number) but the packet mandates a digest; the wire returns the digest string (`credentialRevision`). The frontend can render it as a revision marker unchanged; a counter column would have required mutable state the digest derives for free.
3. **Wire codes are uppercase** (`PROVIDER_UNSUPPORTED`, `PROVIDER_UNAVAILABLE`): the packet names them lowercase, but every wire error code in this API and the `agent_steps.error_code` DB CHECK (`^[A-Z][A-Z0-9_]{2,63}$`) are uppercase-snake; the names are otherwise identical. The OpenAPI schema description documents the lowercase `provider_unsupported` token for continuity.
4. **Unsupported protocols open no agent run**: the packet's failed-run recording requirement is pinned to unreachable providers (run opens, provider call fails, run finishes `failed` — locked by test). For `anthropic`/`gemini` the protocol check precedes run creation because no provider execution is ever attempted — §8.6 records agent runs, and there is no run to record. If reviewers prefer recording an aborted run for every attempt, moving the protocol check after `startRun` is a two-line change plus one test adjustment.
5. **Input hash covers the generation input, not the rendered prompt text**: `input_hash` = sha256 of the canonical `{schema, targetObjectType, targetObjectId, baseRevisionId?, target, instruction, outputSchema}` payload. The agent-attribution echo (run id, config revision, inputHash value) is server-derived from the run itself and injected into the prompt text only — hashing it would be circular (the attribution contains the hash). The hashed payload and the rendered prompt differ only by the fixed header lines and that echo.
6. **Change-set digests are recomputed server-side from the model's before/after values** (canonical sha256), so a live-generated change-set is truthful even though the T003 wire accepts opaque digests. When the model omits an inline value (schema-legal for some add/remove shapes), the model-provided digest is kept.
7. **Cost mapping is normalized usage**: `cost_micros = prompt_tokens + completion_tokens` (one micro per token). No pricing table exists in the vocabulary; pricing adapters are expected to land with the remaining provider protocols. The run/step records still satisfy §8.6's cost+duration contract.
8. **Capability mapping**: model-config mutations use `workspace.manage` (only `workspace_admin` holds it — the administration action closest to provider configuration), reads use `workspace.read`; generation itself uses `asset.propose` per the packet. No new action rows were seeded and the action vocabulary is untouched.
9. **`enable/disable` is folded into PUT** (`enabled` boolean) rather than dedicated sub-routes, mirroring the view's toggle switches; `set-default` is a dedicated POST because it is a state-moving command with cross-row effects. The default flag of a disabled model is NOT cleared (the view keeps showing it as the configured default); `set-default` refuses disabled models/providers with 409.
10. **`base_url` is mandatory for `openai_compatible`** (no default exists for a generic router) and optional for `openai` (defaults to `https://api.openai.com/v1`), matching the view where the Base URL field appears only for OpenAI-compatible providers.
11. **Snapshot fidelity**: the generation target snapshot ships address coordinates, lifecycle/schema-version metadata and the stored content JSON — bounded, workspace-scoped stored data. Raw prompt text is never persisted (the run carries hashes only, per the T002 schema).
12. **`docs/specs/m2-governed-authoring/packets/T009.yaml` is untracked** in the working tree (input packet, not a deliverable); no spec files were modified. An untracked `T010.yaml` appeared in parallel (founder's parallel execution) and was left untouched.
