## 1. 产品定义

### 1.1 一句话定义

Semlia 是一个以 Cube Core 为可执行语义内核、以 LLM Wiki 为知识组织与协作范式的 AI-first 数据语义中台。

**Semlia is an AI-first data semantics platform built on Cube's executable semantic layer and a living wiki for organizational meaning.**

Semlia 把指标、维度、业务概念、关系、证据和消费契约组织成可执行、可验证、可版本化，并可由人、应用与 AI Agent 共同维护和使用的语义资产。

### 1.2 使命

让每一个重要业务概念和指标都具备明确含义、负责人、证据、版本、依赖关系和消费契约，使人类与 AI 可以基于相同事实协作。

### 1.3 愿景

Semlia 成为语义资产领域的开放控制平面和事实协议：

- 团队使用 Semlia 管理语义资产，而不是在 SQL、看板、文档和 Prompt 中重复维护定义。
- 数据产品通过稳定 API、SDK、CLI 和事件接口消费语义。
- AI Agent 通过 MCP 获取经过治理的事实、证据和允许执行的动作。
- 任何语义变更都可解释、可验证、可审核、可回滚并可评估影响。
- 开源社区能够扩展执行引擎、数据源、验证器、策略和消费端集成。

### 1.4 产品本质

Semlia 以 Cube Core 提供可执行语义，以 LLM Wiki 组织企业含义，并以语义资产生命周期连接二者。对话和 Agent 是交互方式，资产图谱、权威页面、治理工作流、不可变发布与消费契约才是产品核心。

LLM Wiki 是由人类与 AI 协作维护的活语义知识系统，不是由模型自由改写的文档集合。每个资产都有一个权威页面，集中呈现定义、计算口径、所有者、血缘、证据、测试、变更历史、使用情况、风险和适合 AI 使用的上下文。AI 负责发现缺口、建立候选关系和生成结构化提案，发布事实仍由验证、策略和审核决定。

## 2. 战略定位

### 2.1 解决的问题

- 指标和业务概念散落在 SQL、BI 看板、数据模型、文档和个人经验中。
- 同名指标存在不同口径，变更缺少影响分析和消费者通知。
- 数据目录描述“有什么”，但通常不能保证“应该如何理解和使用”。
- 自然语言问数依赖临时 Prompt 和模型猜测，缺少稳定语义与证据。
- AI 可以生成语义定义，却缺少可靠的验证、审核、发布和回滚机制。
- 下游应用很难绑定一个明确的语义版本，导致结果随上游变化而漂移。

### 2.2 差异化

Semlia 的差异化不来自更强的 NL2SQL，而来自以下闭环：

1. 从现有系统发现语义和证据。
2. 由 AI 生成结构化提案，而不是直接改写生产事实。
3. 使用规则、编译、查询和评测验证提案。
4. 按资产风险执行分级审核与发布策略。
5. 将不可变语义版本提供给人、应用与 Agent 消费。
6. 根据真实使用、事故和反馈持续改进资产质量。

### 2.3 产品边界

Semlia 是：

- 以 Cube Core 可执行语义层和 LLM Wiki 为基础的 AI-first 数据语义中台。
- 语义资产注册表和关系图谱。
- AI 辅助的语义工程工作台。
- 语义治理、验证、审核、发布和回滚系统。
- 面向应用和 Agent 的语义服务层。
- Cube Core 的首选语义治理控制面，同时保持执行引擎可插拔。

Semlia 不是：

- BI 看板或通用数据可视化产品。
- 自然语言转 SQL 产品。
- 数据仓库、湖仓、ETL 或数据同步平台。
- 只收集元数据而不管理语义生命周期的通用数据目录。
- 新的查询执行引擎或 Cube Core 替代品。
- 默认允许 AI 无约束修改和发布生产语义的自动化工具。

### 2.4 产品组合

| 产品 | 定位 | 关系 |
| --- | --- | --- |
| Semlia | AI-first 数据语义中台和开源语义治理层 | 组织企业含义，管理语义资产的发现、验证、审核、发布与消费 |
| Cube Core | 首选可执行语义内核 | 负责编译、查询执行、访问控制和预聚合，执行 Semlia 发布的兼容语义模型 |
| Fluxale | Agent BI 和参考消费端 | 作为 Semlia 的首个真实消费者和体验验证场 |

### 2.5 Cube 集成边界

- Cube Core 负责语义模型编译、查询规划、查询执行、执行期访问控制和预聚合；Semlia 不复制这些运行时能力。
- Semlia 负责稳定语义资产身份、LLM Wiki、发现、证据、关系、AI 提案、验证编排、审核策略、不可变 release、消费者 binding 和审计。
- Semlia 通过公开 Cube 合约和模型工件集成，不 fork Cube，也不依赖 Cube 私有实现。
- Agent 请求指标结果时，Semlia 解析已发布资产、release、证据和策略上下文，再通过适配器将执行委托给 Cube Core。
- Cube 的 BI、Dashboard、Workbook、对话分析和执行运维界面不属于 Semlia 产品范围。
- Cube Core 是第一优先级集成。Semlia 的核心领域模型保持引擎无关，其他语义运行时只在真实需求出现后通过明确适配器接入。

## 3. 产品原则

### P-001 语义是资产，不是 Prompt

重要定义必须拥有稳定 ID、结构化内容、负责人、版本、证据和生命周期。Prompt 只能引用语义资产，不能成为事实来源。

### P-002 AI 生成提案，策略决定权限

AI 的每次写入都必须形成可审计提案。是否允许自动发布由策略、风险、验证结果和权限共同决定，不能由模型自行判断。

### P-003 发布版本不可变

每个消费者都可以绑定明确的 release。发布内容只能通过新版本演进，不能静默修改。

### P-004 证据优先

定义、建议、验证和 Agent 回答都应返回来源、版本和推理所依赖的证据。找不到可信资产时，系统必须明确返回未解析状态，而不是编造答案。

### P-005 Git-native，但不要求用户理解 Git

语义内容以可读、可 diff、可导出的文件形式存在。产品 UI 封装分支、提交和审核细节，开发者仍可使用标准 Git 工作流。

### P-006 Headless first

所有核心能力先形成稳定服务契约，再由 Web UI、MCP、CLI、SDK 和插件复用。UI 不得成为唯一操作入口。

### P-007 开放执行生态

Cube Core 是第一优先级集成，不将 Semlia 核心领域模型绑定到单一执行引擎。适配器通过明确契约接入。

### P-008 默认安全和最小数据暴露

Semlia 默认只读取元数据、语义定义和受控样本，不复制客户事实明细。所有权限、密钥和 Agent 工具遵循最小权限原则。

### P-009 世界一流来自可靠性

视觉质量重要，但可信度来自确定性、性能、可观测性、兼容性、文档、测试、故障恢复和长期维护承诺。

## 4. 目标用户

### U-001 语义负责人

数据治理负责人、指标负责人和数据产品负责人负责定义、审核、发布和废弃语义资产，并处理冲突与事故。

### U-002 分析工程师

分析工程师维护 Cube、dbt 或 SQL 模型，希望自动发现语义、验证变更、分析影响并减少重复文档工作。

### U-003 AI 与应用工程师

工程师通过 API、MCP、CLI 或 SDK 将可信语义提供给 Agent、内部应用、搜索、BI 和自动化流程。

### U-004 分析师与业务专家

业务专家补充领域含义、示例、边界条件和责任归属，并在不直接修改代码的情况下参与审核。

### U-005 平台管理员

管理员管理工作区、身份、权限、密钥、策略、集成、审计、备份和升级。

## 5. 核心用户旅程

### J-001 建立工作区

1. 管理员创建工作区并配置身份、角色和默认发布策略。
2. 用户连接 Git 仓库、Cube 项目和数据仓库元数据访问凭据。
3. Semlia 只请求完成发现与验证所需的最小权限。
4. 系统执行连接检查并生成可审计的首次扫描记录。

成功结果：团队在十分钟内看到第一批待治理资产和明确的下一步操作。

### J-002 发现与导入语义

1. 连接器读取 Cube YAML、数据库结构、查询样本和已有文档。
2. 系统建立物理字段、模型、维度、度量、指标和业务概念之间的候选关系。
3. AI 为缺失描述、同义词、负责人、测试和关系生成带证据的提案。
4. 用户按风险和影响范围批量处理提案。

成功结果：现有语义被结构化导入，来源和不确定项清晰可见。

### J-003 定义和审核资产

1. 用户或 AI 创建提案，提案绑定基础版本和变更原因。
2. 系统展示结构化 diff、依赖变化、消费者影响和兼容性风险。
3. 验证器执行 schema、引用、编译、数据、策略和评测检查。
4. 审核人接受、修改或拒绝提案，所有决策进入审计记录。

成功结果：没有语义变更绕过策略和验证直接进入已发布事实。

### J-004 发布和回滚

1. 通过审核的资产组成 release candidate。
2. 系统生成不可变 release manifest、内容哈希、Git commit/tag 和兼容性报告。
3. 发布事件通知绑定消费者，并提供迁移信息。
4. 出现问题时，管理员将消费者重新绑定到上一稳定 release。

成功结果：任何发布都可复现，任何消费结果都能追溯到具体版本。

### J-005 面向应用和 Agent 消费

1. 消费者使用稳定 ID 和 release 约束请求语义。
2. Semlia 根据身份、策略和用途返回允许访问的定义、关系和证据。
3. MCP 以只读资源和受控工具向 Agent 提供上下文。
4. 写操作默认创建提案，不能通过 MCP 直接绕过治理发布。

成功结果：不同产品使用相同语义事实，并能解释内容来自哪里。

### J-006 反馈与持续治理

1. Semlia 采集资产解析、使用、失败、变更影响和消费者反馈事件。
2. 系统识别无人负责、长期未验证、低使用、高冲突和高风险资产。
3. AI 生成修复、合并、废弃或补充验证建议。
4. 负责人通过治理流程处理建议并发布新版本。

成功结果：语义资产质量随使用持续提高，而不是导入后逐渐失真。

## 6. 核心能力地图

### C-001 语义注册表与活的 Wiki

- 稳定资产 ID、别名和命名空间。
- 结构化定义与适合人类阅读的页面。
- 所有者、标签、状态、可信度和认证标识。
- 血缘、依赖、证据、测试、消费者和历史。
- 精确、模糊、结构化和语义检索。

### C-002 发现与连接器

- Cube schema 双向适配器。
- 数据库和仓库元数据扫描。
- dbt manifest/catalog 导入作为第二优先级适配器。
- SQL、文档和查询日志证据提取。
- 增量扫描、差异检测和来源可追溯性。

### C-003 AI 语义工程 Agent

- 缺失语义补全。
- 重复与冲突检测。
- 指标、维度和实体关系建议。
- 测试与示例生成。
- 兼容性和影响分析解释。
- 批量提案、失败恢复和人工接管。

### C-004 治理与审核

- 基于资产、工作区和环境的发布策略。
- 所有者、审核人和职责分离。
- 结构化 diff、评论、批准、拒绝和变更请求。
- 分级 AI 自主权。
- 完整审计、回滚和紧急变更流程。

### C-005 验证与评测

- Schema 和引用完整性检查。
- Cube 编译和查询 dry-run。
- 数据质量、边界值和一致性测试。
- Breaking change 检测。
- 策略和权限检查。
- 面向 Agent 的语义检索与回答评测集。

### C-006 发布与注册

- 不可变 release 和 manifest。
- 语义化版本与兼容性声明。
- 环境推广、批准、回滚和废弃窗口。
- 发布签名、校验和与供应链元数据。
- 消费者绑定与变更通知。

### C-007 消费接口

- REST API 作为规范服务契约。
- MCP 作为 AI Agent 首选接口。
- CLI 作为本地开发和 CI 接口。
- TypeScript SDK；其他语言客户端通过同一 OpenAPI 契约按需求生成。
- Webhook 和事件订阅。
- 可导出的 Cube、JSON 和 Markdown 工件。

### C-008 可观测性与反馈

- 资产使用、解析和错误事件。
- 变更影响、废弃进度和消费者健康。
- Agent 工具调用与结果追踪。
- 质量趋势、所有权覆盖率和语义债务。
- OpenTelemetry 指标、日志和链路。

## 7. 领域模型

### 7.1 核心对象

| 对象 | 定义 |
| --- | --- |
| Workspace | 隔离权限、策略、资产和发布的租户边界 |
| Repository | 承载语义文件和发布引用的 Git 仓库 |
| DataSource | Cube、仓库、dbt 或其他发现来源 |
| SemanticAsset | 具有稳定 ID 的语义身份 |
| AssetRevision | 资产在特定内容哈希下的不可变版本 |
| AssetRelation | 两个资产或资产与物理引用之间的有类型关系 |
| Evidence | 支持定义、提案或验证结论的可追溯材料 |
| Proposal | 针对一个基础版本的结构化变更建议 |
| Review | 人或受控 AI 审核者对提案的决策 |
| ValidationRun | 一组可复现验证器的输入、输出和证据 |
| Release | 一组不可变资产版本及其兼容性和策略结果 |
| Consumer | 使用 Semlia 语义的应用、Agent、团队或服务 |
| Binding | 消费者与特定 release 或版本范围之间的契约 |
| UsageEvent | 语义解析、读取、失败或反馈事件 |
| Incident | 与错误语义、发布或消费影响相关的治理事件 |

### 7.2 资产类型

- `concept`：业务术语和领域概念。
- `entity`：客户、订单、账户等业务实体。
- `model`：可查询的逻辑数据模型或 Cube。
- `dimension`：用于分组、过滤或描述的属性。
- `measure`：可聚合的基础度量。
- `metric`：具有业务含义、时间语义和计算规则的指标。
- `segment`：可复用的业务过滤和受众定义。
- `policy`：访问、发布、质量或使用策略。
- `contract`：输入、输出和兼容性约束。
- `test`：针对资产行为和数据结果的可执行验证。

表、列、文件和查询作为 `physical_reference` 管理。它们可以成为语义资产的证据和来源，但不会自动获得业务语义地位。

### 7.3 核心关系类型

- `contains`
- `depends_on`
- `derived_from`
- `measures`
- `describes`
- `filters_by`
- `joins_to`
- `synonym_of`
- `replaces`
- `validated_by`
- `owned_by`
- `consumed_by`
- `evidenced_by`

关系必须包含来源 revision、创建主体、置信度和有效 release 范围。

### 7.4 资产生命周期

```text
discovered -> draft -> proposed -> validating -> in_review -> released
                                                        |          |
                                                        v          v
                                                     rejected   deprecated -> retired
```

- `discovered` 只表示系统观察到候选内容，不代表可信。
- `released` 是唯一可被生产消费者默认使用的状态。
- `deprecated` 必须包含替代资产、通知范围和截止时间。
- `retired` 资产仍保留历史和审计，但不能建立新绑定。

## 8. AI 自主权与发布治理

### 8.1 发布等级

| 等级 | 名称 | 允许行为 | 默认适用范围 |
| --- | --- | --- | --- |
| G0 | Protected | AI 只能读取和生成草稿，指定人类负责人批准 | 核心财务、合规、权限和高影响指标 |
| G1 | Human Review | AI 可提交提案和运行验证，人类审核后发布 | 新工作区和普通生产资产的默认等级 |
| G2 | AI Reviewed | 独立 AI 审核、全部验证和策略门通过后可发布，人类收到通知 | 低风险文档、别名、示例和兼容性补充 |
| G3 | Autonomous | 策略允许时自动提案、验证、发布和回滚 | 经过长期评测证明安全的低风险资产集合 |

新工作区默认使用 G1。G2 和 G3 必须由管理员按资产类型和环境显式启用，不能由 Agent 自行提升。

### 8.2 风险计算输入

- 资产类型和业务重要性。
- 依赖和消费者数量。
- 是否改变计算结果或访问范围。
- 是否属于生产环境。
- 验证覆盖率和近期失败历史。
- 提案置信度与证据完整度。
- 提案者、审核者和发布者的职责分离要求。

### 8.3 AI 行为契约

- 每个结论返回资产 ID、revision、release 和证据引用。
- 每个写操作创建 proposal，并记录基础版本和结构化 patch。
- 模型输出在进入领域层前必须通过 schema 校验。
- 工具权限由服务端策略强制执行，不能依赖 system prompt。
- 同一模型输出不能同时充当高风险变更的唯一提案和唯一审核证据。
- 超时、工具失败、证据不足或版本冲突时进入可恢复状态，不自动扩大权限。
- 所有 Agent run 记录模型、配置、输入哈希、工具调用、输出、费用、耗时和最终状态。

## 9. 对外服务契约

### 9.1 REST API

REST API 是规范接口，所有其他客户端能力应映射到相同领域操作：

- 资产检索、读取和解析。
- 关系、血缘和影响分析。
- 提案创建、验证、审核和状态查询。
- release 创建、读取、比较和绑定。
- 消费者注册、绑定和使用反馈。
- 策略、身份和审计管理。

所有读取支持明确的 `release` 或 revision 约束。未指定时只返回工作区配置的稳定 release，不返回未发布草稿。

### 9.2 MCP

MCP 是 Agent 的首选语义接口：

只读资源：

- 工作区资产目录。
- 单个资产的已发布页面。
- release manifest。
- 领域术语、策略和关系视图。

核心工具：

- `search_assets`
- `get_asset`
- `resolve_metric`
- `explain_lineage`
- `analyze_impact`
- `validate_context`
- `list_release_changes`
- `create_proposal`

MCP 不提供绕过审核的直接生产发布工具。发布动作只能调用受服务端策略保护的统一领域命令。

### 9.3 CLI

CLI 支持本地开发和 CI：

```text
semlia init
semlia pull
semlia ingest
semlia diff
semlia validate
semlia propose
semlia release
semlia mcp
```

CLI 输出默认同时支持人类可读格式和稳定 JSON 格式。自动化命令必须提供可预测退出码。

### 9.4 SDK 与事件

- 首发提供 TypeScript SDK，其他语言客户端保持契约兼容但不进入首发工具链。
- SDK 由 OpenAPI 合约生成基础客户端，并增加少量领域友好封装。
- Webhook 使用签名、重试、幂等键和事件版本。
- 核心事件包括资产变更、验证完成、审核决定、release 发布、绑定风险和资产废弃。

## 10. 系统架构

### 10.1 架构形态

```text
Web / CLI / SDK / MCP / Integrations
                 |
          Semlia Control API
                 |
  Domain services and policy engine
        |          |          |
   PostgreSQL     Git      S3 / MinIO
        |
 Postgres-backed worker and outbox
        |
 Cube adapter / dbt adapter / warehouse metadata adapters
        |
 Cube Core executable semantic kernel and customer data platforms
```

Semlia 的控制平面不进入 Cube Core 的查询执行路径。Cube adapter 将 Semlia 的语义 release、验证请求和运行上下文映射到公开 Cube 模型与 API，并把编译、查询和评测结果作为可追溯证据返回 Semlia。

### 10.2 技术基线

| 层 | 选择 |
| --- | --- |
| Web | React、TypeScript、Vite |
| 控制面运行时 | Go 1.26，模块化单体，单一 `semlia` 可执行文件提供 server、worker、mcp、migrate 和 doctor 子命令 |
| API | OpenAPI-first REST，Go `net/http`，生成边界类型和严格 handler 接口 |
| AI 与 MCP | 显式可恢复 Agent 状态机、JSON Schema 输出校验、官方模型与 MCP Go SDK |
| 数据访问 | pgx v5、sqlc、显式 repository 和事务边界 |
| 迁移 | golang-migrate 管理的版本化 SQL migration |
| 控制面数据库 | PostgreSQL 17 或更高版本 |
| 文件与证据 | S3 兼容对象存储，开发环境支持本地文件系统 |
| 语义内容版本 | 内嵌或外部 Git 仓库 |
| 后台任务 | PostgreSQL job table、outbox、`FOR UPDATE SKIP LOCKED` |
| 查询执行 | Cube Core 首选，适配器契约保持开放 |
| 可观测性 | OpenTelemetry |
| 本地部署 | Docker Compose |
| 集群部署 | Helm 和 Kubernetes |

第一阶段保持模块化单体。同一个 Go 构建工件可按 server、worker 和 MCP 等角色分别运行，Web 静态产物可嵌入二进制或独立部署。生产运行不依赖 Node.js。只有当独立扩缩容、故障隔离或团队所有权产生可测需求时才拆分服务。

## 11. 数据与存储决策

### 11.1 权威边界

- Git 是已发布语义内容的权威来源。
- PostgreSQL 是工作流、索引、权限、关系和审计状态的权威来源。
- 对象存储是大型证据和生成工件的权威来源。
- 客户数仓是事实数据的权威来源。
- Cube runtime 和本地 SQLite 只保存可重建的执行状态或缓存。

任何内容都不能同时拥有两个无法确定优先级的权威来源。PostgreSQL 中的已发布内容快照必须能由 Git commit 和 content hash 验证。

### 11.2 PostgreSQL 核心表组

```text
workspaces, memberships, roles, policies
repositories, data_sources, connector_runs
semantic_assets, asset_revisions, asset_relations
evidence, proposals, proposal_changes, reviews
validation_runs, validation_results
releases, release_assets
consumers, bindings, usage_events, incidents
agent_runs, agent_steps
jobs, outbox_events, audit_events
```

稳定身份、生命周期、权限、外键和可查询状态使用规范化关系字段。扩展定义、编译 AST 和适配器负载使用有 schema 版本的 `JSONB`。

### 11.3 图、搜索和向量

- 血缘和影响关系首先使用 `asset_relations` 邻接表、索引和递归 CTE。
- 名称、别名和结构化字段首先使用 PostgreSQL 索引和 `pg_trgm`。
- 英文文档使用 PostgreSQL 全文检索；中文内容采用预分词或经过验证的中文检索扩展。
- 语义召回达到明确需求后，在 PostgreSQL 中加入 `pgvector`。
- 只有复杂多跳算法成为核心负载且 PostgreSQL 实测不达标时才引入图数据库。
- 只有搜索规模、语言能力或排序质量实测不达标时才引入独立搜索引擎。

### 11.4 数据保留

- 发布版本、审核、审计和安全事件不可原地修改。
- Agent 输入中可能包含的敏感样本按工作区策略脱敏和限期保留。
- 使用事件按租户和时间分区，并支持聚合后删除明细。
- 删除工作区执行可验证的异步删除流程，并保留合规要求允许的最小审计证明。

## 12. 安全、隐私与合规

### S-001 身份和授权

- 支持本地开发身份和生产 OIDC/OAuth 2.1 集成。
- 使用工作区 RBAC，并为高风险发布支持职责分离。
- API token 具备明确 scope、过期时间和撤销能力。
- 服务端对每个领域命令执行授权，客户端隐藏按钮不构成安全控制。

### S-002 密钥和连接

- 密钥不写入 Git、日志、Agent prompt 或普通数据库明文字段。
- 默认使用信封加密，并支持外部 KMS 或 Secrets Manager。
- 数据源连接遵循只读、最小权限和可轮换原则。

### S-003 数据访问

- 默认不采集客户事实明细。
- 数据验证优先使用聚合、采样、脱敏和仓库内执行。
- 每次跨边界读取记录目的、主体、资产、策略和结果摘要。

### S-004 供应链

- 发布包含依赖锁定、SBOM、镜像签名和校验和。
- CI 执行依赖、密钥、容器和静态安全扫描。
- 安全披露流程、支持版本和响应目标公开可查。

### S-005 审计

所有资产写入、权限变化、提案、审核、发布、回滚、密钥操作和 Agent 工具调用生成不可抵赖的审计事件。

## 13. 非功能需求

### NFR-001 性能

- 在 100,000 个资产和 1,000,000 条关系的基准工作区中，单资产读取 p95 不高于 150 ms。
- 结构化搜索 p95 不高于 500 ms。
- 三跳影响分析 p95 不高于 1 s。
- 10,000 个资产的增量扫描和基础验证在 5 分钟内完成。
- UI 首次可交互时间在标准宽带和推荐部署规格下不高于 2.5 s。

### NFR-002 可靠性

- 托管版控制面月度可用性目标为 99.9%。
- 已接受的写命令支持幂等重试。
- 发布和审核状态转换使用事务和乐观并发控制。
- 稳定 release 回滚操作在 2 分钟内完成。
- 备份恢复演练至少每季度执行一次。

### NFR-003 可解释与可复现

- 100% 的生产语义响应可追溯到 release 和 revision。
- 100% 的 AI 写入可追溯到 proposal、证据和策略决策。
- validation run 记录工具版本、输入哈希和结果。
- 相同 release 导出产生确定性内容和哈希。

### NFR-004 可访问性

- Web 产品满足 WCAG 2.2 AA。
- 所有核心流程可使用键盘完成。
- 状态、风险和错误不能只依靠颜色表达。
- 动效尊重 reduced motion 设置。

### NFR-005 可观测性

- API、任务、连接器、Agent 和发布流程使用统一 trace ID。
- 核心 SLI 包含延迟、错误率、队列积压、验证成功率和发布失败率。
- 日志结构化、可脱敏，并包含稳定错误码。

### NFR-006 兼容性

- REST、事件、文件 schema 和 MCP 工具均有显式版本。
- Breaking change 只进入主版本，并提供迁移工具和废弃窗口。
- 插件 SDK 在一个主版本周期内保持兼容承诺。

### NFR-007 自托管体验

- 新用户使用 Docker Compose 在 5 分钟内启动完整本地环境。
- 从连接示例 Cube 项目到发布首个资产不超过 10 分钟。
- 所有必要配置都有校验、示例和可操作错误信息。

## 14. 质量与交付标准

### 14.1 Definition of Done

任何用户可见能力只有同时满足以下条件才算完成：

- 需求和边界有稳定 ID 和验收标准。
- 领域行为具备单元和集成测试。
- 关键用户旅程具备端到端测试。
- 权限、失败、空状态、并发和回滚路径经过验证。
- API、CLI、MCP 和 UI 行为保持契约一致。
- 文档、迁移和可观测性同步完成。
- 性能与安全风险有证据或明确接受记录。
- 变更经过至少一次独立评审。

### 14.2 测试金字塔

- 领域层：确定性单元测试和属性测试。
- 数据层：PostgreSQL 真实实例集成测试和迁移测试。
- 适配器：契约测试、录制样本和故障注入。
- Agent：固定评测集、工具调用轨迹和模型供应商兼容测试。
- Web：组件可访问性测试和 Playwright 核心旅程。
- 发布：安装、升级、备份、恢复和回滚测试。

### 14.3 发布门禁

- Schema 和引用完整性通过。
- 数据库向前与回滚迁移经过验证。
- Cube 适配器编译和查询验证通过。
- Breaking change 和影响报告生成。
- 安全扫描没有未接受的 Critical 或 High 问题。
- 文档、示例、changelog 和升级说明完整。
- 候选版本在全新环境完成安装测试。

## 15. 开源产品策略

### 15.1 开源承诺

建议采用 Apache License 2.0。以下能力属于完整可用的开源核心：

- 语义资产模型、注册表和 Wiki。
- Cube 连接器和开放适配器 SDK。
- AI 提案、验证、审核和发布工作流。
- REST、MCP、CLI 和基础 SDK。
- 本地与单集群自托管。
- RBAC、审计和基础可观测性。

商业化聚焦于托管服务、企业支持、跨区域高可用、组织级合规包、托管连接器和运营 SLA。商业版本不得让开源自托管产品失去完成核心语义治理闭环的能力。

### 15.2 社区原则

- 公共路线图和公开 RFC。
- 重要架构决策使用 ADR。
- 贡献使用 DCO，避免不必要的版权转让门槛。
- 遥测默认关闭，启用前明确展示内容和用途。
- Issue 和 PR 使用稳定模板、响应目标和维护者标签。
- 每个 release 提供签名工件、升级说明和兼容性矩阵。
- 插件、连接器和验证器拥有独立开发指南与 conformance test kit。

### 15.3 生态飞轮

1. 高质量 Cube 集成带来第一批真实语义资产。
2. MCP 和 SDK 让 AI 与应用获得稳定价值。
3. 消费事件反哺资产质量和影响分析。
4. 社区贡献更多连接器、策略包、验证器和模板。
5. 更丰富的生态提高 Semlia 作为开放语义控制面的标准价值。

## 16. 成功指标

### 16.1 北极星指标

**Weekly Trusted Semantic Resolutions**：每周由已发布资产成功解析，并返回明确 release、revision 和证据的 API、SDK、CLI 或 MCP 请求数量。

### 16.2 激活指标

- 80% 的新工作区在 10 分钟内完成首个数据源连接。
- 60% 的新工作区在 30 分钟内发布首个语义资产。
- 首次 Cube 导入中 90% 的有效模型和指标被正确识别。

### 16.3 信任指标

- 100% 的生产响应可追溯到不可变 release。
- 发布后 7 天内因错误语义触发的回滚率低于 1%。
- 高风险资产所有者覆盖率达到 100%。
- 已发布资产验证覆盖率达到 95%。

### 16.4 效率指标

- 常规语义变更从提案到发布的中位时间低于 1 个工作日。
- AI 生成且经用户少量修改后接受的提案比例高于 50%。
- Breaking change 的已识别消费者覆盖率达到 100%。

### 16.5 开源指标

- 首个稳定版发布后 12 个月内形成至少 20 个外部贡献者。
- 维护者对可复现缺陷的首次响应中位时间低于 3 个工作日。
- 至少 5 个非官方连接器或验证器通过 conformance test。

## 17. 路线图

路线图按可验证的产品闭环推进，不按页面或技术层横向堆功能。

### M0 产品与工程基础

目标：建立可持续开发和开源发布基础。

- 确认本 SSOT、许可证、仓库治理和品牌。
- 建立模块化单体、迁移、测试、CI、安全扫描和发布流水线。
- 提供 Docker Compose、本地开发脚本和贡献指南。
- 固化领域 schema、错误模型、审计事件和版本策略。

退出标准：全新贡献者可在 15 分钟内运行测试和示例环境。

### M1 Semantic Registry

目标：从 Cube 项目得到可信、可浏览、可版本化的语义资产。

- Cube 导入与增量扫描。
- 资产页、关系图、搜索、所有权和证据。
- Git 内容存储与 PostgreSQL 索引。
- 基础 diff、revision 和审计。

退出标准：真实 Cube 项目可以无手工迁移地形成可浏览资产图谱。

### M2 Governed AI Authoring

目标：AI 可以安全参与语义工程，而不是停留在聊天建议。

- Agent run、proposal 和结构化 patch。
- 验证器框架与 Cube 编译验证。
- G0/G1 发布等级、审核工作台和 release manifest。
- 冲突检测、影响分析和回滚。

退出标准：团队可完成“AI 提案、验证、人类审核、发布、回滚”的完整闭环。

### M3 Semantic Distribution

目标：其他产品和 Agent 稳定消费 Semlia。

- 版本化 REST API。
- MCP server 与只读资源。
- CLI 和 TypeScript SDK。
- 消费者注册、release 绑定、Webhook 和使用事件。

退出标准：Fluxale 和至少一个独立 Agent 在生产式流程中只通过 Semlia 获取语义。

### M4 Continuous Governance

目标：真实使用数据持续改善资产质量。

- 质量评分、语义债务和负责人队列。
- 废弃、迁移和消费者通知。
- Agent 评测集与 G2 发布等级。
- dbt 适配器和第二类消费端集成。

退出标准：资产质量、冲突和废弃进度可以量化，并形成周期性治理闭环。

### M5 Open Ecosystem

目标：Semlia 成为可扩展的开放语义控制面。

- 连接器、验证器、策略和导出插件 SDK。
- Conformance test kit 和兼容性认证。
- Helm、OIDC、备份恢复和高可用运行手册。
- 经过长期安全评测后开放受控 G3 能力。

退出标准：外部团队无需修改核心代码即可发布和维护生产级插件。

## 18. 首个公开版本范围

### 必须包含

- Cube 项目导入和增量刷新。
- 核心资产类型、稳定 ID、revision 和关系。
- 资产 Wiki 页面、搜索、血缘和影响分析。
- AI 生成结构化 proposal，并展示证据和 diff。
- Schema、引用、Cube 编译和策略验证。
- G0/G1 审核、不可变 release 和回滚。
- 只读 REST、MCP 和 CLI 消费路径。
- 工作区 RBAC、密钥保护和审计。
- Docker Compose、自托管文档和示例项目。

### 明确不包含

- 通用 BI 看板设计器。
- NL2SQL 和自然语言问数主界面。
- 自建 OLAP 或查询引擎。
- Neo4j、Elasticsearch、Kafka 和独立向量数据库。
- 无策略约束的 AI 自动发布。
- 同时支持大量浅层连接器。
- 面向所有数据治理场景的通用数据目录功能。
